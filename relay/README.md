# Relay

How a phone reaches its Mac from anywhere, with nothing to set up: the paid part of Kiko (Kiko Pro). A Cloudflare Worker with one Durable Object per Mac (a room). The Mac and each phone connect out to it over a WebSocket, and it passes what one sends to the other. It never sees what they say: the phone and the Mac run an end-to-end encrypted tunnel through it (Noise IK, keyed at pairing on the home network), so every frame after a phone joins is opaque bytes to it.

**Public with the app**, so anyone can see it only passes encrypted bytes along; production's abuse limits are a secret, not in the code ("Limits"). It's a package of its own (its own `package.json`, `pnpm-workspace.yaml` and lockfile), so Kiko's install never pulls in wrangler.

**Phase 1** (built 2026-11-01): the relay, the Mac's side (`src/remote/relay-client.ts`, `tunnel.ts`, `relay-identity.ts`, on only with `KIKO_RELAY_URL`), the protocol (`protocol/README.md`, "Relay", and `protocol/relay-vectors.json`), and tests. The iPhone app speaks it since (its `relay-client`). Abuse limits added the same day ("Limits"). Deployed at `wss://relay.kiko.sh` ("Deploying"); still nobody uses it until they set `KIKO_RELAY_URL`.

## What it does

- `src/index.ts`: the Worker routes `/v1/mac/<room>` and `/v1/phone/<room>` (WebSocket upgrades only; a room is 32 hex characters) to the room's Durable Object, named by the room id.
- **The Mac** signs in by signing the room's fresh challenge with its Ed25519 key; the room id is derived from that key (the first 16 bytes of its SHA-256), so only that Mac can open it. With `requirePass` on (the default) it must also show a good relay pass for the room ("The pass"), so only a holder of one can claim the room or displace the Mac there. A Mac signing in again replaces the old socket and lets its phones go. It registers its phones' relay credentials, as SHA-256 hashes only.
- **A phone** joins with its credential (32 bytes from the Mac at `relay_pair`); the room checks the hash, gives it a channel, and tells the Mac. From then on its binary frames go to the Mac behind 4 bytes of channel, and the Mac's back to it the same way. A Mac that goes takes its phones with it; a forgotten credential closes its phone.
- **Pairing by the QR code from away:** while the Mac shows its pairing QR code it registers one more hash (`pairing`), of a credential drawn from the code's secret, for at most 5 minutes: it lets one phone in per registration, on a channel the Mac is told is `pairing`, then says `qr_used` (4012) to the next; once shut by the Mac, run out or past 5 phones, `qr_expired` (4013). The Mac's close of such a channel can carry `qr_used` or `qr_expired`, which the phone hears. `ready` says `pairing: true` so a Mac knows this relay takes it (an older relay says nothing, and is sent nothing). `protocol/README.md`, "Pairing through the relay".
- **Hibernation:** sockets are accepted with the WebSocket Hibernation API, and what each one is (the Mac or a phone, signed in or not, its channel) lives in its attachment, so the object can be evicted between frames and an idle room costs nothing. `ping` is answered with `pong` by the runtime itself (`setWebSocketAutoResponse`), without waking the room. An alarm closes sockets that haven't signed in or joined within 10 seconds.
- **Storage:** a few keys per room: the credential hashes, the last channel number, the room's usage, and the pairing code's credential hash (with until when, whether it's spent, how many phones it let in). Nothing else is kept: no keys, no tokens, no frames.
- **Limits** (`src/limits.ts`): message size, messages per second, a room's bytes per window and per day, sign-in and half-open sockets, each role's budget of waiting sockets and the per-address limits in a room, and new rooms per address and per account (in shared state: `src/limiter.ts`, the `Limiter` Durable Object); the abuse limits' production numbers come from the `RELAY_LIMITS` secret. Below, "Limits".
- **The pass** (`src/pass.ts`): the iPhone app needs Kiko Pro or the free trial (decided 2026-11-04). The Mac shows its room a relay pass from our account server; with `requirePass` on, the Mac signs in and a phone joins only with a good one (`plan_required`, 4014). **On by default** since 2026-11-19 (a missing or malformed `RELAY_LIMITS` fails closed). Below, "The pass".

The wire format, every message, close code and byte of the tunnel: `protocol/README.md`, "Relay".

## Limits

Anyone can make an Ed25519 key, so anyone can open a room and, with a phone credential of their own, push bytes through it: without limits a public relay is a free tunnel. Each limit is far above what Kiko sends, and each has its close code (`protocol/README.md`, "Relay": limits, which the iPhone app goes by). They're in `src/limits.ts`, in two kinds.

**The protocol's** (`PROTOCOL`): what the Mac and the phone build on, so they're in the code and in `protocol/README.md`, and production never changes them:

| limit | number | why |
|---|---|---|
| binary message | 1 MiB + 1 KiB | The largest real frame is a tunnel record: 1 MiB of plaintext at most (`MAX_RECORD` in `src/remote/tunnel.ts`, the hub's own WebSocket limit), +1 type byte, +16 of tag, +4 of channel. Audio is tiny beside it (an Opus frame is five 20 ms packets, ~300 bytes; a PCM `audio` chunk in JSON ~6.5 KB), but a `history_page` or the project list can be a few hundred KB, so the cap is the tunnel's, not the audio's. Cloudflare itself takes up to 32 MiB. Over: `too_big` 4008. |
| text message | 16 KiB | Text is only the relay's own: `auth` (~150 bytes, ~700 with a pass), `join` (~60), `pass` (~600), the Mac's `phones` (32 hashes, ~2.2 KB), `close`. Checked before sign-in too, so nothing big is parsed for a stranger. |
| signing in | 10 s | A socket that hasn't signed in or joined in 10 s is closed (`timeout` 4005), and nothing before that is ever passed along: a Mac's socket only signs in, a phone's only joins, and any other first message closes it (`bad_message` 4006). |
| half-open | 90 s | A signed-in Mac or a joined phone with no sign of life (a message, or a `ping` the runtime answered: `getWebSocketAutoResponseTimestamp`) for 90 s is closed (`idle` 4011). The Mac pings every 10 s (25 s until 2026-11-13; these pings never wake the room and aren't counted against its rate limit, so the tighter beat costs it nothing); a phone answers the hub's pings every 15 s. Checked whenever the room is awake, before a phone joins (so it's never told a dead Mac is there), and by the alarm, which is set only while a socket is signing in or a phone is in the room: a room holding only its Mac gets no alarm and sleeps for free. |
| phones, credentials | 10 phones in a room; 32 credentials | `too_many` 4004 for an eleventh phone; the Mac's list is cut at 32 (in `src/index.ts`). |
| pairing by a QR code | one phone per registration; 5 minutes; 5 phones in all | The code's own rules on the Mac (one phone, 5 minutes), held by the room too, so a photo of an old code, or someone holding the credential, can't keep joining: a registration lets one phone in (`qr_used` 4012 after), the Mac registers it again only when that phone didn't pair, the hash lives at most `pairingMs` from its first registration however often it's registered, and lets `pairingJoins` phones in over that life (then `qr_expired` 4013). A wrong credential is `unauthorized`, as ever, and costs a socket's join like any (the waiting sockets, the message bucket). |

**The abuse limits** (`DEFAULTS`): how hard a room may be used. Production's numbers aren't in this repo: knowing them would let a flood aim just under them. The deployed relay reads them from the **`RELAY_LIMITS` secret** (below), and the code holds only defaults; production sets its own. The defaults are round numbers, safe for a relay run without the secret (well above what a Mac and its phones send):

| limit | key | what it counts |
|---|---|---|
| messages per socket | `phoneRate`, `macRate` (`{ perSecond, burst }`) | A token bucket per socket, in memory (full again after hibernation). A phone sends ~10 a second while it talks (a frame per 100 ms) and a pong every 15 s; the Mac ~10 a second per phone it speaks to, up to ten phones, plus bursts at connect (welcome, sessions, history), so its bucket is bigger. `ping` is answered by the runtime and never counted. Over: `rate_limited` 4009. |
| a room's bytes | `windowMs`, `windowBytes`; `dayMs`, `dayBytes` | Binary frames both ways, every phone together, per window and per day; each window starts with its first byte. For scale: Opus is ~3 KB/s each way (10 minutes of nonstop talk and speech both ways: ~4 MB); with Compressed audio off, PCM is ~46 KB/s up and ~65 KB/s down (10 minutes of nonstop speech: ~40 MB). The budget is set well above the worst real case, while capping a room's average rate so it's useless as a tunnel. Counted in memory, written to storage every 1 MiB, on going over and as a socket closes, so a room evicted from memory keeps its day (losing at most the last MiB). Over: every phone gets `over_quota` 4010 with `retryIn` (seconds), joins are refused until then, the Mac is told once and stays signed in, its frames dropped. |
| sockets waiting | `pending` (10), `macPending` (2) | Sockets in a room still signing in or joining, each role with a budget of its own (phones; Macs without a good pass in the upgrade), so strangers waiting as phones never keep the Mac out. A role's budget full: its oldest waiting socket goes (`timeout` 4005) for the new one, so whoever holds the slots must keep making sockets, which the next two make slow. A Mac with a good pass for the room in its upgrade (`Kiko-Relay-Pass`) waits outside every budget and per-address limit, one per account (a newer one replaces it): strangers can't keep it out at all. (M8 of the 2026-11-19 review: a room id is in the pairing QR code.) |
| waiting per address | `pendingPerIp` (3), `ipRate` (`{ perSecond: 1, burst: 10 }`) | Per room, per address (`CF-Connecting-IP`; IPv6 by its /64, `src/address.ts`; only a short hash of it kept, in the socket's attachment): the waiting sockets it holds at once, and a token bucket of the new sockets it opens (in the room's memory). Over: HTTP 429. |
| new rooms per address | `roomsPerIpHour` (20), `ipsTracked` | At the Worker, before any room, for a Mac's upgrade without a good pass: new rooms an hour per address (IPv6 by its /64), a room already seen from it always passing (a Mac reconnecting). Counted in shared state, the `Limiter` Durable Object named for the address (`src/limiter.ts`), behind a per-isolate map (holding at most `ipsTracked` addresses) that stops a flood from one address cheaply. Over: HTTP 429; the shared count not answering: 503 (never let through uncounted). |
| rooms per account | `roomsPerAccount` (8), `roomsPerAccountMs` (24 h) | A Mac's upgrade with a good pass, at the Worker (HTTP 429 over it), and a sign-in whose pass came only in `auth` (`too_many_rooms` 4016): the distinct rooms the pass's account (`sub`) opened in the window, in the `Limiter` named for the account. A pass is for one room, so this caps how many Macs one subscription powers (L10: the account server doesn't yet ask for proof of the room's key). |

**`RELAY_LIMITS`** is a JSON object with any of those keys (`{"pending": 20, "macRate": {"perSecond": 300, "burst": 1500}, …}`, every number made up here). It's read once per isolate and checked: a key left out keeps its default (as does half of a rate left out), a value that isn't valid (not a positive number, a count that isn't whole, a rate that isn't `{ perSecond, burst }`) keeps its default and is named (never its value) in a warning, an unknown key is ignored, and anything that isn't a JSON object leaves every default. Production sets the abuse limits only. Tests set their own as a plain var, with small numbers and short windows, and may shorten the protocol's timings too (`signInMs`, `idleMs`) to run quickly; they never use production's.

**Cloudflare's own rate limiting.** The Workers Rate Limiting binding (`ratelimits` in `wrangler.jsonc`) counts calls per key per 10 or 60 seconds, approximately and per location. Its numbers (`simple: { limit, period }`) can only be set in the wrangler config (read at deploy, not from a secret or a var), so if it's ever added its numbers are public: give it a neutral, generous value (a flood guard, not a tuned threshold) and say so beside it. It can't count distinct rooms or hold an hour, so it doesn't fit new rooms per hour; it would fit a flood of connection attempts per address, which the room's own limits make cheap anyway. A WAF rate limiting rule on the zone (the Free plan has one, 10-second periods) is the other option for a flood, and its numbers live in the dashboard, not here. Neither is on now; worth adding one before a public launch, once it's checked against the account's plan.

## The pass

Decided 2026-11-04: Kiko's iPhone app, at home and away, comes with **Kiko Pro or the free trial**. Through the relay, the relay checks it. The wire format: `protocol/README.md`, "Relay", "The pass".

- **The pass** is a compact JWS (EdDSA) from our account server (`POST https://api.kiko.sh/v1/relay/pass`, the Mac sending its room id), for `aud` `relay.kiko.sh`, issued by `https://account.kiko.sh`, with the account (`sub`), its plan (`trial` or `pro`), the Mac's `room`, `iat` and an `exp` **24 hours** on (7 days until 2026-11-04; never past the plan's own end). The relay takes none living longer than `passMaxLifeMs` (26 hours) from its `iat`: a 7-day pass from before is `invalid`. The Mac shows it in `auth`, and renews it on the open socket (`{"type":"pass"}`) with under 12 hours left or as soon as its plan changes.
- **Checked here with no call per pass** (`src/pass.ts`): the signature against our JWKS (`https://account.kiko.sh/v1/jwks`, then `https://api.kiko.sh/v1/jwks`; `PASS_JWKS_URL` overrides, for tests), cached an hour per isolate (a failed fetch keeps the old keys), fetched again for an unknown `kid` at most every 10 seconds; then `iss`, `aud`, `plan`, `room`, `exp`. The result is held in the Mac socket's attachment (so it survives hibernation), never in storage.
- **The last good JWKS, kept:** in the KV namespace `kiko-relay-pass-keys` (binding `PASS_KEYS`, one key `jwks`: each key's `kid` and `x`, public keys only), with no expiry, written only when a fetch brings keys that differ from it (never an empty set). An isolate that can't fetch the JWKS and has none in memory reads it from there, so passes are still checked in an outage; it tries the account server again every 10 seconds at most meanwhile.
- **The revocation list** (`src/revoked.ts`): access that ends before a pass runs out (a ban, the account deleted, a Mac signed out by itself or from the account page, signed out everywhere, the plan ending or taken away) is written by the account service to the KV namespace `kiko-relay-pass-revoked` (binding `PASS_REVOKED`, `368bf570dd0d4d4abd17a2833875f77f`). Keys: `sub:<account id>` (the whole account) and `room:<account id>:<room id>` (one Mac signed out); value `{"at":<Unix s>,"until":<Unix s>}`. A pass whose `iat` is before an `at` is **`revoked`**, refused like `invalid` (`plan_required`, the Mac told `pass: "revoked"`); one issued after works at once. Read only with `requirePass` on: as the Mac signs in, when a phone joins a room whose Mac's pass is otherwise good, and while phones are in the room about once every `revokedCacheMs` (the alarm comes at least every `idleMs` then), so **a revocation also lets the phones already in go** (`plan_required`; the Mac hears `phone_refused` with `revoked` and asks for a new pass). One bulk get of the two keys, kept in the Room's memory for `revokedCacheMs` (60 s). **KV not answering fails closed:** a read from within `revokedStaleMs` (10 minutes) still stands, else the pass is `unverified` and the sign-in or the join is refused; the check of phones already in does nothing then (an outage never cuts anyone off). Why not fail open: the list is billing's only way to end access within the day, and KV is rarely away; why the 10 minutes: a blip shouldn't refuse a room that read the list a moment ago. Each entry expires on its own at `until`, 26 hours after the event (the pass's 24 and 2), so `passMaxLifeMs` must stay no longer than that. **One namespace, two Workers:** Cloudflare lets Workers of the same account bind one KV namespace by its id, so the account server writes the list and the relay reads it, nothing passing between them but KV (simplest: no service binding, no endpoint). How fast: the account server's write, KV's spread to the relay's location (up to a minute), and a room's cached read (up to a minute): about two minutes at most. Costs: a join reads 2 keys (bulk reads are billed per key), at most once a minute per room; the Free plan's 100,000 key reads a day are far off.
- **Never a lockout, never on trust:** a phone already in stays when the pass runs out (only a revocation lets it go); a pass lasts 24 hours, so an account server outage keeps phones away from home joining for up to a day (checked against the kept keys; at home the Mac's own 7-day last-known-plan grace holds, unchanged). A failed payment's 7-day grace keeps Pro, so the Mac keeps renewing its pass through it. Only when no JWKS was ever fetched (nothing kept), or the server is away and a pass's `kid` isn't among the kept keys, can a pass not be checked: it's `unverified`, and refused (with `requirePass` on) like `invalid`. Key rotation works as ever through the unknown-`kid` fetch.
- **The room:** a pass names the room it's for; one for another room is `invalid`, and so is one without `room`, with `requirePass` on or off (since 2026-11-19; L10). The account server must still check the Mac holds the room's key before it mints a pass for it (below, "Still to do").
- **The switch, `requirePass`** in `RELAY_LIMITS` (a boolean; `src/limits.ts`), **on by default** since 2026-11-19: a `RELAY_LIMITS` without the key, not JSON, or not set at all is on. Off only with `"requirePass": false` (development, tests): every room works without a pass; a phone let in without a good pass is only logged (`console.log`, with nothing identifying). On: a Mac signs in only with a good pass for its room, not revoked (else `plan_required` 4014 with the pass's status; one `revoked` hears a `phone_refused` with it first, so a Mac from before this asks for a new pass), and a phone joining a room whose Mac's pass isn't good now hears `plan_required` (4014), and the Mac `phone_refused`. A phone of a room whose Mac was refused in the last day hears `plan_required`, not `mac_offline`.

**Turning it on: the order** (so Macs on 0.3.10 and 0.3.11 with the phone on keep working; they show their pass in `auth` only, a few seconds after the first dial):

1. **Deploy this relay with `"requirePass": false` in `RELAY_LIMITS` first.** The code's default is now on, so a deploy with a `RELAY_LIMITS` lacking the key turns it on at once. Add `"requirePass": false` to that JSON and put it again (below) before `wrangler deploy`. The deploy adds the `Limiter` class (migration `v2`) and the new limits; with it off, nothing changes for anyone but the new limits.
2. **Release the Mac app with this branch** (it shows the pass in the upgrade header too, waits for it before the first dial, and waits for a new pass after a refusal instead of redialling). Not required for 0.3.10/0.3.11 to keep working, but it makes their phones' first join faster and their Macs immune to strangers in the waiting slots.
3. **Turn it on:** remove `"requirePass"` from `RELAY_LIMITS` (or set it `true`) and put it again. Takes effect at once, no deploy. What happens to each Mac:
   - 0.3.10/0.3.11 with Pro or the trial: its first dial after a restart may come before its pass (refused, `plan_required`); it dials again within about a second, with the pass in `auth`, and signs in. Signed in already: untouched until it reconnects. Its renewals (`{"type":"pass"}`) work as before.
   - 0.3.10/0.3.11 with no plan: refused at each dial (it backs off to a minute), its phones told `plan_required`. Harmless; it costs a request a minute per such Mac with Phone on.
   - This release, with the plan: signs in on the first dial. With none: one dial, then it waits for a pass (an hour at most).
   - Kiko Dev (a checkout) with a trial or Pro account: the same as this release (it asks the same account server for its pass).
4. **Check:** a throwaway Mac's `ready` says `"passRequired": true`, and one without a pass is refused with `plan_required`. Back off: `"requirePass": false` again.

```sh
<the JSON, on stdin> | WRANGLER_SEND_METRICS=false pnpm --dir relay exec wrangler secret put RELAY_LIMITS --name kiko-relay
```

The end-to-end test (`KIKO_RELAY_TEST_URL`, below) has no pass: against a deployed relay with `requirePass` on its Mac is refused.

To deploy again (the machine needs `wrangler login` once):

```sh
pnpm --dir relay typecheck && pnpm --dir relay test
WRANGLER_SEND_METRICS=false pnpm --dir relay exec wrangler deploy
```

**`RELAY_LIMITS`**, production's abuse limits, is a secret on the Worker, set apart from the code and kept across deploys, so a deploy doesn't touch it. Its numbers are kept out of this repo: no file here holds them, and they're never passed as an argument. To set or change it, pipe the JSON on stdin (from wherever you keep it, outside the repo):

```sh
<the JSON, on stdin> | WRANGLER_SEND_METRICS=false pnpm --dir relay exec wrangler secret put RELAY_LIMITS --name kiko-relay
```

`secret put` makes a new version of the Worker at once, with the code already deployed. A relay without it runs on the code's defaults; one with a key that isn't valid keeps that key's default (`src/limits.ts`). `wrangler secret list --name kiko-relay` shows it's there, never its value. On a new Worker, set it before sending it traffic.
