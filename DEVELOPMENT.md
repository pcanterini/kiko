# Developing Kiko

The working reference for Kiko from a checkout: the window and its tmux, the command line, the keys, connecting each agent, and how to try it all by hand. What users read is `README.md` (install, first run, troubleshooting; the details it leaves out are at the end of this file) and `PRIVACY.md`; how to run the checks and send a change is `CONTRIBUTING.md`.

Talk to your coding agents: a voice layer for Claude Code on the Mac (and Codex CLI, OpenCode and T3 Code: their sections at the end). `kiko` (or `pnpm start`) opens it in one window (below); its settings (Ctrl+Space `s`) pick the voice, hotkey and the rest. How it's put together: `ARCHITECTURE.md`; what each agent's sessions get, feature by feature, and what's missing: `SUPPORT.md` (written by `pnpm support`; a new feature is declared for every agent, ARCHITECTURE "What each agent supports").

The iPhone app isn't open source: it lives in its own repo. It talks to Kiko only through `protocol/`, whose source of truth is here; the app keeps a copy of it.

## The Kiko window and tmux

Since 2026-10-29 (merged into `main`), tmux is the main way Kiko types into your sessions, and Kiko and your sessions share one window. A session started in Kiko's own tmux can take your words at any moment, not only right after it speaks, wherever it's shown (or with no window at all). Without tmux, or for sessions started with plain `claude`, everything works as before through Ghostty. A session in the Claude desktop app is heard and answered right after it speaks, through its hooks, but Kiko never types into the desktop app (that took the clipboard): words for it at other moments aren't sent, and Kiko says so.

### The Kiko window
```
┌ Kiko ───────────────┬ pixie ───────────────────────────────────────┐
│ 0      Kiko          │                                              │
│ ── SESSIONS ──          │  the real Claude Code: you type, scroll and  │
│ 1 ▸ ✻  pixie   ● idle   │  use its shortcuts as always                 │
│ 2   ⌬  lacy ● working   │                                              │
│ ── OUTSIDE ──           │   (or Kiko's own page, or an outside      │
│ 3   ✻  notes   ● idle   │    session's conversation, read-only)        │
│ + new session (c)       │                                              │
│ c new  ⇥ session  ⌃Space menu                                          │
├─────────────────────────┴──────────────────────────────────────────────┤
│ ● Kiko is ready · ⚠ pixie needs you   hold right ⌥ to talk · ⌃Space menu ☰ Kiko │
└────────────────────────────────────────────────────────────────────────┘
```
- **`kiko`** opens it in the terminal you run it from. It starts Kiko (the app: mic, hotkey, voice, phone) in it unless Kiko is already running; it never starts a second one. Running `kiko` in another terminal just shows the same window there too.
- **Ctrl+Space is the menu key**, from anywhere in the window, even while you're typing in Claude (Claude Code doesn't use it; the window takes nothing else from Claude). It opens the menu, which is also the cheat sheet. **Pressed twice** it goes to the session shown, as tmux's prefix does (for a program there that wants Ctrl+Space). **The ☰ Kiko button** at the bottom line's right end opens the same menu with a click, so there's always a way in without the key. The key can be another one (the "Menu key" setting, `--key`, `KIKO_KEY`), and when your own tmux, herdr, Warp or your Mac takes Ctrl+Space first, Kiko takes another for that run and asks whether to keep it: see "Inside your own tmux or herdr", below. Every hint names the key in use. One key means one thing everywhere in Kiko, tmux's letter where tmux has one:

  | Key | Does |
  |---|---|
  | `0` | Kiko's own page (below) |
  | `1`–`9` | that session, numbered as in the list (outside ones say "(outside)") |
  | `Tab` | the keyboard between the list and the session; first under the pages, it says where it goes: "Go to the session →" from the list, "Go to the list ←" from the session side |
  | `n` `p` | the next or previous session, in the list's order (round the ends) |
  | `l` | the last one: the page shown before this one |
  | `c` | a new session: the project picker |
  | `s` (or `,`) | settings, over the whole window (Escape comes back) |
  | `d` | hide the window: this terminal goes back to its shell; Kiko keeps listening, sessions keep running |
  | `q` | quit Kiko: "Press q again to quit · your sessions keep running"; `q` again (or `Q`, or `y`) within 2 s quits, any other key goes back to the menu and does nothing else, and so does the time running out |
  | `r` `i` `x` | the session shown, or the outside one whose conversation is shown (under a line with its name): Rename…, Interrupt (Escape), Close this session… (it asks first: `y`); outside Kiko's tmux, only those it can do there (below) |
  | `↑` `↓`, Enter or Space | move the highlight, pick the line highlighted |
  | `/` | search the menu (below) |
  | Ctrl+Space (the key again) | close the menu and send Ctrl+Space to the session shown (only a session in Kiko's tmux, typed the same checked way as everything Kiko types) |
  | Esc | close the menu |

  **`/` searches it:** a search line comes up at the top (`/ ro▏`), and from then on what you type is the search, not keys (`q` doesn't quit, `2` isn't session 2). The list narrows as you type, best match first: sessions by name, folder or Claude's title (what it matched by shown dim beside it), every menu command by its words (its key still shown), and under a line of their own the settings by name ("voice": `Settings → Voice`, `Settings → Voice engine`…; picking one opens settings on that row). Any case; the words anywhere first, then a word's start, then the starts of words in order (`nese`: Next session), then three or more letters in order (`rky`: pixie); ties keep the menu's order. `↑` `↓` move, Enter picks (what that line would do, Close still asking first and Quit still wanting `q` again), Backspace edits (and, with nothing left, ends the search), **Esc clears the search** and shows the whole menu again; Esc again closes it. Nothing found: "nothing matches", and Enter does nothing. The Kiko key still works as above. Pages past the twelve the menu lists are found too. Without `/`, every key is as before. (A session's right-click menu is short, so it has no search.)

  A key acts at once (Ctrl+Space then `2` shows session 2); the highlight starts on the page shown, so Ctrl+Space `↓` Enter shows the one below it; every line can be clicked too. The menu is made from what Kiko knows at that moment, so new sessions are in it. The session's three are the same as its right-click menu's, and aren't there on Kiko's page or an outside session's conversation. The menus are drawn in your terminal's own colours: its background, a thin blue border, the line highlighted in reverse, keys dim, so they read the same in a dark or a light theme.
- **On the left, the list:** `0 Kiko` first, then every session Kiko knows, numbered, the one shown marked `▸`, each with its state as the phone shows it (needs you, waiting, working, idle). **Working means in a turn:** from your prompt until it stops, never just because something it started still runs in the background (a background shell, a subagent). That shows quietly after its state instead: `● idle · 2 bg` in the window's list (`2 in background` in the classic look and on the phone), with how long when some of it has done nothing for 10 minutes or more, one left over and stuck: `● idle · 3 bg (quiet 8h)`. The "ready · N working" count counts only sessions in a turn. (Claude Code's background jobs say what they run in their own file; a terminal or desktop session's transcript says when each task started and ended, and a session `claude agents` lists as idle runs nothing, so an end never written can't keep a count up. The phone shows the ones still running beside an idle session's state: `idle · 3 agents running`.) **Each session shows its agent:** a mark before its name, mark and name in that agent's colour: `✻` Claude Code in orange, `⌬` Codex in blue, `▣` OpenCode in peach, `⊤` T3 Code in indigo, `◇` any other agent in your terminal's own colour. Each mark has two cells to itself before the space and the name, so the names line up even where your font lacks a mark and the terminal draws it a little wide. Sessions have no colour of their own: two Claude Code sessions are both orange (their numbers and names tell them apart), and the same colour and mark are on the permission card, the new-session picker and Kiko's own page. With a Nerd Font 3.5 or newer, Settings → The Kiko window → **Nerd Font icons** (or `KIKO_ICONS=nerd`) draws Claude Code's and Codex's own icons instead (ARCHITECTURE "Agent marks" says how to install one). Sessions in Kiko's tmux come first; the others (in Ghostty, the desktop app, and Claude Code's background sessions, marked "(background)") are under OUTSIDE, numbered on. A session in the Claude desktop app has a dim `⧉` after its name (in the menu too, in place of "(outside)"); the phone marks it with a small window icon. A number keeps to its session while others get busy or quiet. Then `+ new session`.
  - **Click** a row to show it on the right (the keyboard stays in the list, as for its number): Kiko's page, a session in Kiko's tmux, or an outside one's conversation. Click inside the right side to type there. Click `+ new session` for the picker. **Right-click** a session for its menu: Enter shows it, `r` Rename…, `i` Interrupt (Escape), `x` Close this session… (it asks first); ↑ ↓ and Enter or a click work too. **Close ends Claude Code gracefully:** Escape first if it's mid-turn, then `/exit` typed into it (with the same checks as everything Kiko types), so it saves its conversation and runs its SessionEnd hook; once it has ended (5 seconds at most) its pane and tmux session close. If `/exit` can't be typed or it doesn't end in time, the tmux session is ended as before. The note under the list says which: "Closed lacy. Its conversation is saved." **An outside session** (in Ghostty, Warp, iTerm, herdr, your own tmux, or a background job) can be closed too, from either menu: nothing types `/exit` there, so Kiko sends its Claude Code a SIGTERM, which it takes like `/exit` (it saves the conversation, runs its SessionEnd hook, and its terminal prints "Resume this session with: claude --resume …"); a background job gets `claude stop`. First it checks, right before, that the process is still that session's Claude Code (its record in `~/.claude/sessions`, the process's start time, its program), and sends nothing if not. The question says it ends in its terminal, and "Its current reply will be lost." while it's mid-turn. It waits up to 10 seconds for it to go; if it's still running then, the note says so and Kiko does nothing more. Rename… and Interrupt are there only for a session in a Ghostty window Kiko has found for sure (by its title, or the only Claude window in its folder); for Warp, iTerm, herdr and your own tmux they're left out (Kiko never types into those). A session in the Claude desktop app can't be closed from here: its menu only shows it. **A T3 Code thread** has Rename…, Interrupt and Archive in T3 Code… (`x`, asked first), done through T3's server, not typed (below).
  - **Keys, when the list has the keyboard:** picking here **previews**: `0`–`9` shows that page on the right, `↑` `↓` move the highlight and show each page as you pass it (`+ new session` shows nothing), `n` `p` next and previous, `l` last, all with the keyboard staying in the list, so you can flip through sessions. **Enter** or **→** goes into the one highlighted: it's shown if it isn't, and the keyboard goes there (an outside one's conversation too, to scroll it); Enter on `+ new session` opens the picker. Never Esc (Claude uses it to interrupt): Ctrl+Space Tab is the way back. The menu's other letters: `c` new, `s` (or `,`) settings, `d` hide the window, `q` (or `Q`) quit: the keys' line says "Press q again to quit · your sessions keep running", and `q` again (or `y`) within 2 s (`QUIT_AGAIN_MS`, `src/ui/quit-again.ts`) quits; any other key lets it go and does nothing else, and so does the time running out. Ctrl+C the same, its second press Ctrl+C (or `q`, or `y`), in the list and on the settings screen (the hint in its footer; on the splash, Ctrl+C skips it and the list comes with the hint up). Typing a name, a project or a filter, `q` is a letter; Ctrl+C still asks there, and the key that lets it go isn't typed; plain **Tab** moves the keyboard to the session side (in a session, Tab is Claude's: Ctrl+Space Tab comes back); `r` renames the highlighted session (as its right-click Rename…; nothing on Kiko's row, or on an outside one that has no Rename…), `.` says the last thing again, `m` mute. One key means one thing everywhere: `r` is always rename, `.` always repeat (in the plain full-screen UI too). Drag the line between the list and the session to make the list wider or narrower; it keeps that width when the terminal resizes.
- **A permission prompt or Claude's question** that Kiko holds shows as a card at the bottom of the list, just above its keys (the sessions stay where they are): who asks, what for, and its answers. `y` allow, `a` always, `n` deny (or the option's number for a question, `n` to decline: while a card is up, `n` does only that) with the list focused, a click on the answer, or by voice as always. The bottom line says who needs you too. A session that needs you never takes the right side over: the list, the bottom line and Kiko's voice tell you. Answered in Claude Code's own dialog instead (allowed, denied or Esc there), the card comes down within about a second, while Kiko is still asking out loud too: Kiko watches the session's transcript and its dialog's state for as long as it holds the prompt (ARCHITECTURE.md, "Permission prompts that stand after their window").
- **On the right:** the session you picked, the real Claude Code in its own pane. Or **Kiko's own page** (`0`, what it shows when the window opens): your conversation with Kiko, live, with the time: what you said, what Kiko said, where your words went, quick tasks' answers, sessions asking you things, errors. Or an **outside session's conversation**, read-only and live: its name, where it runs, its state and folder, then what you said, Claude's replies and what Kiko said about it (tool use as one dim line). Both scroll with ↑ ↓ PgUp PgDn Home End or the wheel; scrolled up, new lines don't move them ("↓ 2 new messages", End to jump down).
- **At the bottom, one line:** what Kiko is doing (ready, listening, deciding, speaking), who waits for you or needs you, how to talk and the menu's key, then the **☰ Kiko** button (a click opens the menu). What you're saying shows there only while you say it.
- **Keys go only to the side that has the focus** (its name on the bar above it is bold and blue; the other's is grey), so typing in Claude never sets off Kiko's keys. Ctrl+Space then Tab (either way), plain Tab in the list, or a click moves the keyboard. The talk key (right ⌥) works from anywhere, as always.
- **Closing the terminal doesn't stop anything:** Kiko and your sessions keep running, and `kiko` shows them again.

### What else it does
- **Its own tmux, out of your way.** Kiko runs its own tmux server (`tmux -L kiko`) with its own config (`src/terminals/tmux/tmux.conf`). Your `~/.tmux.conf` isn't read, and your own tmux sessions are never touched. It's set up to feel like no tmux at all: no prefix key (Ctrl+B stays Claude Code's), the mouse wheel scrolls back, Escape gets through at once, 24-bit colour.
- **`kiko claude [args…]`** starts Claude Code in that tmux, in the current folder, and shows it in the Kiko window (opened here, Kiko started if need be). The args go to `claude` as they are.
- **New sessions by voice** ("open a new session in pixie") start in that tmux and show in the Kiko window when it's there (a terminal opens on the window if none shows it). Without the window, they open in a new Ghostty window of their own, as before (Terminal.app if Ghostty isn't installed). A window on Kiko's own opens in the terminal you started `kiko` from when that's Ghostty, iTerm or Terminal (`KIKO_WINDOW_TERMINAL=ghostty|iterm|terminal` picks one), else Ghostty, else Terminal. Every AppleScript to another app runs in the helper app, so macOS asks once whether "Kiko Dev" may control Ghostty (or iTerm, Terminal), not your terminal; Ghostty is only asked for its windows while a session runs there (ARCHITECTURE.md, "The helper app").
- **Which agent a new session starts in** (branch `harness-picker`, 2026-10-30), once more than one that can start sessions is connected (Claude Code, Codex and OpenCode today; Pi would add its own). With only one, nothing here changes: no picker, no question, the same words.
  - **From the window** (`c`, `+ new session`, or the menu's New session): once the folder is picked, a small popup asks which, in the menus' style: "New session in clipkit", one row per agent, "Enter starts · ↑↓ picks · Esc cancels". The row chosen as it opens is the preselected one (marked "this run", "last used" or "your setting"), so Enter alone repeats it.
  - **By voice** (and words from the phone): never asked. An agent you name wins ("start a Codex session in clipkit", "open a Claude session"); otherwise the preselected one starts, and Kiko says which: "Starting a Codex session in clipkit."
  - **From the phone** (its home screen's **New session**, 2026-10-31): the window's picker, on the phone. The projects the Mac knows, newest first (search to narrow), **New project…** (named there, made in the projects root) and **Scratch folder**; then the agents connected for that folder (T3 Code only in its own projects), the preselected one ticked ("last used"); then the first message: typed and **Start**, or held and said on its talk button, and it starts as you let go with your words (written down on the Mac and shown on the phone, never taken as a command: "start a session in pixie" said there is what the new session is told); or none, **Start**, and it just opens. An optional **Name** for it (2026-10-31), where its agent can be named as it starts: on Claude Code's command line (`--name`), T3 Code's title, and for Codex and OpenCode a rename once it's listed, the same rename as the menus' (OpenCode's through its service, at once; Codex's as its rename goes), kept whatever Voice can says (the phone asked, not voice); an agent that can't be named shows the field greyed out, with why. "Starting…" until it's listed, then its chat opens: empty while it starts, then its conversation once its agent lists it (the Mac follows the screen from its starting-… id to the session, whichever agent). Why not, in the Mac's words, in the sheet: "That folder isn't one of your projects any more.", "OpenCode isn't connected…", "I can't open a new terminal on this computer.". Shown, not said, like the window's (Voice can doesn't apply); `harness_picked` and `session_open` say `by: phone`.
  - **The preselected one:** after `kiko codex` (or `kiko claude`), that agent, for that run (until the next plain `kiko`); otherwise the "New sessions in" setting: **Last used** (the default: the agent the last session started from Kiko was in, whichever way it was started), or Claude Code or Codex pinned there. A value pinned before this setting had "Last used" keeps working (an older settings file may have `"newSessionAgent": "claude-code"` from the old settings wizard: pick Last used in settings to change it). `harness_picked` in the log says which and how (`named`, `only`, `picker`, `voice`), with what was preselected and why.
- **The permission mode a new session starts in** (settings → New sessions → Permission mode, 2026-10-30): Accept edits by default, so Claude edits without asking and asks for the rest, and each prompt reaches you as a card, by voice and on the phone. Also Ask me, Plan, Auto, or Your Claude Code default (no flag, as before). Codex gets its nearest (read-only, workspace-write, its automatic reviewer); OpenCode has no flag for any. Only sessions Kiko opens; yours are untouched. A session in another mode than that shows it in the list ("plan", "auto", "bypass"), and when auto mode blocks something (Claude Code's PermissionDenied hook, added by Connect, or "Add the rest" in settings → Agents), Kiko says what: "Auto mode blocked Lacy from running wrangler deploy." For a session in Kiko's tmux that's a card, "… Allow it?": yes switches it to Accept edits (Shift+Tab, its screen read back after each press) and asks it to try again, so the call comes back as an ordinary prompt for you to allow; elsewhere it says why it can't. A call your OpenCode deny rules stop is said too, never overridden. Whatever the mode, the **safety gate** (Settings → Permissions, off by default; turned on) has Kiko ask before anything that sends, deletes, pays or posts, bypass permissions and allow rules included: ARCHITECTURE.md, "The safety gate".
- **Typing only where it's meant to go.** A session is matched to its tmux pane by its process, never by its title, shown in the window or not (and never Kiko's own list). Before every word and key Kiko checks again that the pane still runs that session's process, in front, and tmux checks once more as it pastes, in the same step. If you've scrolled back, the pane comes back to the bottom first. If anything is off, nothing is typed and Kiko says why ("I didn't type that into pixie: its process has ended"). Your words never go on a command line (where any program could read them with `ps`), nor does your environment.
- **`kiko ls`** lists the sessions in Kiko's tmux, and whether the window and Kiko are running; **`kiko attach pixie`** opens the window showing pixie.
- **A new session is listed at once, as "starting".** Claude Code asks "trust this folder?" in a folder it doesn't trust (every new scratch folder), and only starts the session once you answer. Until then Kiko lists it as "starting" (the window, the phone, and what Kiko knows when you talk), by the name you gave it. What you say to it meanwhile is held and typed in once it has started, never into that prompt. If it ends first, Kiko says so, and says that what you'd said for it wasn't sent.
- **Claude Code's "trust this folder?" as a card.** For a session in Kiko's tmux, Kiko reads its pane while it starts, and once Claude Code asks whether to trust its folder, asks you like a permission prompt: a card on the list ("⚠ Dozer wants to trust its folder ~/Kiko/scratch/2026-10-29-dozer", `y` trust, `n` don't trust), out loud ("Dozer wants to trust its folder, 2026-10-29-dozer. Claude Code will be able to read, edit and run files there. Allow?"), and on the phone (a card and, while it's away, a notification), so a session can start while you're away from the Mac. Yes: Kiko moves Claude Code's selection to "Yes, I trust this folder", reads the screen again, and presses Enter only once it sees it picked (the first option is "No, exit"); if it can't, it says so and leaves the question in the window. No: Claude Code exits, and Kiko says what you'd said for it wasn't sent. By voice only when Voice can is "everything" (it starts or ends a session); a tap always works. **It stays up until it's settled**: unlike other cards it has no window and is never answered for you. Once the permission window runs out, a bare "yes" is no longer taken as its answer, but the card stays on the Mac and every phone (no seconds on it, the session "needs you"), and words for that session ask it out loud again. Settled anywhere, it goes from everywhere at once (the Mac's card, every phone's card, the phone's notification): answered on the Mac, by voice or on any phone, answered in its own window (Kiko reads its pane every 3 seconds while the card is up), the session starting (SessionStart), or the session or its pane ending (Kiko closing it too). A session in Ghostty can't be read: after about 10 seconds it shows as needing you, and Kiko says once that it's waiting in its window, probably asking whether to trust its folder.
- **Trust the scratch folder once.** The first time a scratch session opens and Claude Code doesn't trust Kiko's scratch folder, Kiko says so. Say "trust the scratch folder", press Ctrl+Space `t`, or run `kiko trust-scratch`: Claude Code opens in the scratch folder itself, you pick "Yes, I trust this folder" there (the first option is "No, exit"), and Kiko types `/exit` into it once it starts. It's a one-time step, and new scratch sessions don't ask after it. Kiko only reads that one answer from `~/.claude.json` and never writes the file.
- **Quick checks ask before they do more.** "Is kiko.dev taken?", "how much disk space do I have?": with Voice can at "everything", Kiko answers these itself with a quick, look-only Claude Code run (a quick check, `claude -p`), not a session. It may read and search files and run commands that only look (`df`, `ps`, `git status`, … and since 2026-10-29 the name lookups `whois`, `dig`, `host` and `nslookup`, with any arguments). Anything else it wants is asked, like a session's permission prompt: "Kiko's quick check wants to run curl -I kiko.dev. Allow?", by voice ("yes", "no", "always"), on the card in the window (`y` / `a` / `n`) and on the phone (its card and notification, under "Kiko's quick check"; a tap on the notification opens only the card). Its clock stops while it asks.
  - **Never asked, denied outright:** editing files (Edit, Write, NotebookEdit) and git commands that change a repository (commit, push, checkout, reset, stash pop, a new branch, …). A quick check looks; for a change, it says so ("That would change something on your Mac, and a quick check can only look") and offers a session: the project's when it's about one, else one in the scratch folder (never your home folder unless you ask for it).
  - **"Always"** keeps that exact command for quick checks only, in `~/.config/kiko/quick-always.json` (next to Kiko's settings; `{ "commands": [...] }`, edit or delete it to take one back). Claude Code's own settings are never touched. Web fetches and searches are asked every time, never "always".
  - **No answer** within the permission window (Settings → Permissions) is a no, and so is a request with Kiko not running: the quick check answers with what it couldn't check. Then Kiko offers once: "I couldn't check that quickly. Want me to open a session for it?" Yes opens a session (in the quick check's folder) with the task as its first message; no leaves it.
- **A session's chat on the phone** (2026-10-31; needs the iPhone app rebuilt): its replies headed with who answers in their agent's colour, Markdown and code drawn properly (long ones behind Show more), tool steps folded into one line with each file edit as a diff card, what it's doing now while it works ("● Running pnpm build…"), its question or permission inline with quick replies (Deny / Always / Allow), one bar for typing and hold-to-talk with Interrupt while it works, a ⋯ menu (its permission mode, Rename, Close, as far as the Mac can do them), long-press to Copy or Hear it again, and earlier messages as you scroll up. The iPhone app's `README.md`, "A session (the chat)"; the protocol in `protocol/README.md`, "A session's screen".
- **Summaries keep what matters, and "more" by voice** (2026-10-31). Each finished turn's summary is as it was: the outcome in a sentence or two, and its question. **Summary length** (settings → Replies) has four levels: Brief (the outcome in a few words), Just the gist, A sentence or two (the default), Detailed (the main points); the two old ones are unchanged, and a saved one keeps its meaning. Brief and Detailed are also told never to drop what the reply says still fails, wasn't done, or wasn't checked. Measured on 84 real replies (`tests/eval/summary.ts`). Right after a summary, or any time for the last thing a session said, say **"more"**, "tell me more", "details" or "what else?" (with the session's name too: "Lacy, more") for a longer summary of that same reply, or **"more about the failing tests"** / "what did it say about the migration?" for all it says about that part ("It didn't say anything about the migration." when it doesn't). Kiko says it itself; it's never typed into the session, and a turn waiting for your reply keeps waiting. Works from the phone's talk button too. Words like "you missed…" or a question back right after a summary are logged (`summary_feedback`) as cases for the summary eval (`tests/eval/summary.ts`).
- **"Can you hear me?" is Kiko's** (2026-11-04). "Can you hear me?", "are you there?", "testing, one two three", "hello?", "is this thing on?", said alone (with "hey", "okay" or "Kiko" around them at most), are answered by Kiko at once, with no model: "Yes, I hear you.", "Loud and clear.", "I'm here.", never the same twice in a row. Whoever you dealt with last, is waiting or just spoke; a turn waiting for your reply keeps waiting. Words that only start that way ("testing the api endpoint now", "can you hear the audio in the video?") or name a session ("Lacy, are you there?") go where they always did (`routing-rules.ts` `livenessCheck`). Less clear ones ("did you get that?") are the classifier's, which now counts these checks as the app's, and the router answers them. Logged as `liveness`; the eval cases are tagged `liveness`.
- **Two sessions in one sentence each get their part** (2026-11-07). "Tell Harbor to deploy and tell Atlas to tag the release v3.2.0." sends Harbor "Deploy." and Atlas "Tag the release v3.2.0.", each a send of its own (said where it goes, held when it would be, cancellable as any); "Tell Mintbox to add the export button and Pixie to update the screenshots.", "Tell Harbor to roll back. Atlas, hold the release." and "Tell Atlas and Harbor to pull main." too. Each part is your words with the direction to it, the "and" and the other's part left out, never rewritten; a part said another way ("and ask Atlas whether it's tagged") goes as said. A first part that names no session is the reply to the one waiting ("Yes, and tell Harbor to deploy."). When the words can't be cut into one part each, nothing goes and Kiko asks for each one's part. Words for one session that only mention another ("Tell Bobby that MintBox already fixed the cert") go to it whole, as before (`sessions.ts` `splitBySession`, `decide.ts` step `split`).
- **Words said to Kiko by name stay with Kiko** (2026-11-07). "Tell Atlas to run the tests, and Kiko, slow down when you read the results." sends Atlas "Run the tests"; "… Thanks Kiko.", "…, Kiko, you don't need to read back the reply" and "hold on Kiko, let me think" aren't passed on either. Only words said *to* Kiko (its name with a pause after it, or "thanks Kiko"), by the name set in Settings; Kiko as what the work is about stays ("the Kiko overlay doesn't show the latest text", "make Kiko's bars wider"). A thanks or the name at the very end is left out in code; the rest by the trim, which only deletes. A "don't" after Kiko's name is left out only when it's about Kiko itself (reading out, speaking, speed, listening, waiting); "Tell Pixie to make the button bigger, Kiko, don't change the colours." keeps "don't change the colours" for Pixie. Kiko doesn't act on them yet (slowing down, not reading back).
- **Questions to Kiko about a session are Kiko's** (2026-11-07). "Is Harbor still deploying?", "Hey Kiko, what's the status for MintBox?", "What was the finding on MintBox?" are answered from what Kiko knows (each session's status, what it last said, the recent conversation); when that isn't enough, Kiko says so and asks "Want me to ask Harbor?", and a yes sends your question there. They're never typed into the session unasked. A question said to the session ("Bobby, are you still deploying?", "MintBox, what was the issue?") goes there as before, and so does a reply to the one waiting (`sessions.ts` `askedAbout`, `decide.ts` step `about`, the router's `<asks_you_about>`).
- **Words never go nowhere silently.** When the words name a session that isn't there, Kiko says so ("I don't see a session called dozer."). When nothing at all came of them, it says "I didn't do anything with that: …", logs `nothing_done`, and the phone shows it as failed.
- **← parks a session** (Claude Code 2.1.312): ← on an empty prompt opens Claude Code's agents view, and the session is moved into a background job there. Kiko lists it once, under its own name, and its pane is still where your words go. You can turn this off in Claude Code's `/config` ("← opens agents").

### `kiko`'s command line
```
Usage: kiko [options] [command]

Commands:
  (none)                open the Kiko window here (starts Kiko if it isn't running)
  claude [args…]        start Claude Code here, in the Kiko window (args go to claude as they are)
  codex [args…]         start Codex here, in the Kiko window (args go to codex as they are)
  opencode [args…]      start OpenCode here, in the Kiko window (args go to opencode)
  attach [name]         the Kiko window, showing that session (kiko ls lists them)
  ls                    the sessions in Kiko's tmux
  trust-scratch         trust Kiko's scratch folder in Claude Code, once (it asks there)
  setup [--all]         set Kiko up: your agents, one key, the microphone, the talk
                        key, its voice; the steps done already left out (--all: every one)
  setup <agent>         connect an agent: add Kiko's hooks to its file, or repair
                        them (claude, codex, opencode). Asks first; yours are kept, and
                        the file is backed up
  uninstall [agent]     take Kiko's hooks out of an agent's file (only Kiko's; none:
                        every one). Installed with install.sh, plain uninstall takes all of
                        Kiko off this Mac, asking first (and again for the logs)
  keys                  the API keys, and where each comes from (never shown)
  keys set <name>       enter one (hidden): checked, then kept in the Keychain
                        (openrouter, anthropic, deepgram, cartesia)
  keys remove <name>    take one out of the Keychain
  update                install the newest Kiko now (it starts the next time Kiko does)
  update --rollback     go back to the version before
  help                  this text

Options (before the command):
  --key <key>           the menu key, which opens the window's menu (Ctrl+Space by
                        default): C-Space, C-\, C-], C-g, M-k, F12, or Ctrl+], Alt+K…
  -h, --help            this text
  -V, --version         the version

KIKO_KEY=<key> is --key <key>. --key wins over KIKO_KEY, which wins over the
"Menu key" setting. When your own tmux, herdr or macOS takes that key first,
Kiko uses another one that time (Ctrl+\ first) and says so.
```
(As `kiko -h` prints it: `src/cli-args.ts` USAGE. A checkout's command is `kiko-dev`.)
- **Options go before the command** (`kiko --key F12 claude`). Everything after `claude` goes to Claude Code untouched, so `kiko claude --resume x -p` passes `--resume x -p` to it. The usual long-option rules: `--` ends the options, and short ones cluster (`-hV`).
- **An unknown option is an error** with what you probably meant (`kiko: unknown option --hlep. Did you mean --help?`), and so is an unknown command or an argument a command doesn't take. Usage errors exit with 2.
- **`--key <key>`** (or `--key=<key>`) takes a value, the only option that does; a key Kiko can't use is a usage error that says why (`kiko: --key: C-c can't be the menu key: Ctrl+C is the terminal's own (interrupt)`).

### Always in tmux
Kiko always runs as its window, in its own tmux. The `--no-tmux` and `--tmux` flags and the "Use tmux" setting are gone, and so is Kiko's full-screen run in a terminal of its own: `pnpm start` is `kiko` now.
- **Which tmux:** an installed copy (the one-line install, `RELEASING.md`) brings its own, built for each release (`current/bin/tmux`), and its server always runs that one: nothing to install, and your own tmux is never used for it. A checkout uses the tmux on your PATH (`KIKO_TMUX_BIN` names another). Sessions in your own tmux are yours, as before.
- **tmux not installed (a checkout):** `kiko` stops and says so (`kiko: Kiko needs tmux, which isn't installed (brew install tmux)`), and so do `claude`, `codex`, `opencode`, `attach`, `ls` and `trust-scratch`. A run that prints and quits (`kiko claude -p`) needs no tmux: it's plain `claude -p`.
- **Sessions you start yourself** outside Kiko's tmux (plain `claude` in Ghostty or another terminal, T3 Code, the desktop app, Codex, OpenCode) are heard and answered as before.

**Something that runs inside a Kiko session** (Claude Code's own shell) gets where it is from `KIKO_KEPT_TMUX`.

### Inside your own tmux or herdr
Kiko's window can run inside your own tmux, or in a herdr pane, as in any terminal: `kiko` there opens it inside. Ctrl+Space goes through your tmux to Kiko's (your tmux's own keys, Ctrl+B and the rest, stay yours: Kiko's tmux has no prefix).

**The menu key.** Ctrl+Space unless you pick another:
- **The "Menu key" setting** (settings, under "The Kiko window"; `menuKey` in the settings file): Ctrl+Space, Ctrl+\, Ctrl+], F12, Ctrl+G, Alt+Space. Changed there, it works at once in every terminal showing the window. By hand in the settings file, any key in tmux's names that Kiko can use: Ctrl with Space, a letter or `\ ] ^ _` (not Ctrl+C, D, H, I, J, M or Z: the terminal's own), Alt (Option, with "Option as Alt" in your terminal) with a key, Ctrl+Alt with a letter, or an F key.
- **`--key <key>`** for one run, and **`KIKO_KEY`** in your shell. Which one counts: **`--key` > `KIKO_KEY` > the setting > Ctrl+Space**. Written as tmux does (`C-Space`, `C-\`, `M-k`, `F12`) or the usual way (`Ctrl+Space`, `ctrl+]`, `⌃Space`, `Alt+K`, `Option+K`).
- **One key for the whole window**: it's bound in Kiko's tmux, so the last `kiko` decides. Two terminals where one needs a fallback and the other doesn't: the one run last wins, and ☰ Kiko works in both.

**When something takes Ctrl+Space first**, `kiko` sees it as it opens the window (it only reads, never changes your setup):
- **Your own tmux**: its prefix or prefix2 is the key, or its root table binds it (`tmux show -gv prefix`, `show -gv prefix2`, `list-keys -T root C-Space`, asked of the tmux you're in).
- **herdr**: its `[keys]` prefix in `~/.config/herdr/config.toml` (or the file `HERDR_CONFIG_PATH` names) is the key. herdr's default is Ctrl+B.
- **Your terminal app**: one whose own default shortcut is the key, known by `TERM_PROGRAM` (only that variable is read). Today that's **Warp**, whose Ctrl+Space opens a new pane (Warp issue #5149; clearing the shortcut doesn't always free it). iTerm2, Terminal.app, Ghostty, kitty, Alacritty and WezTerm use neither Ctrl+Space nor Ctrl+\ out of the box, so nothing is asked there. Inside your own tmux or herdr, `TERM_PROGRAM` names them, not the terminal around them, so a Warp around a tmux isn't seen: set the key yourself there.
- **Your Mac**: "Select the previous input source" (⌃Space, in System Settings → Keyboard → Keyboard Shortcuts → Input Sources) is on, and you have more than one input source to switch between. With one, it does nothing and doesn't count.

Then Kiko uses **Ctrl+\** that time (Ctrl+] when that's taken too, then F12), the window opens at once (nothing waits for you), and Kiko **warns you and asks**. The warning is said out loud and shown on the bottom line: "Warp uses Ctrl+Space for a new pane, so the menu key is Ctrl+\ this time. Keep it, or pick your own?" The question is a popup over the window, drawn like the menu, saying which program takes the key:
- **`y` (or Enter): Use Ctrl+\ from now on.** Remembered for that clash: next time Warp (or the same tmux prefix, and so on) takes Ctrl+Space, Kiko uses Ctrl+\ without asking, and only shows "Warp uses Ctrl+Space for a new pane. The menu key is Ctrl+\ then, as you chose." Elsewhere (Ghostty, say) Ctrl+Space stays the key.
- **`s`: Set my own key in settings.** Settings open on "Menu key"; the key you pick works at once. Ctrl+\ until then.
- **Escape: neither.** Ctrl+\ this run, and the next `kiko` asks again.

The answers are kept in the settings file as `keyClashAnswers` (by clash: what took which key, and the key used instead, so a different clash is asked about anew). Picking a key in settings clears them. A key from `--key` or `KIKO_KEY` is only warned about, not asked ("… this time. Change it in settings."), and so is a clash with no free key left. Why Ctrl+\: every terminal sends it as it is (one byte), it's neither tmux's nor herdr's prefix, macOS, Warp and Claude Code don't use it, and what it does in a plain terminal (quit with a core dump) nobody presses on purpose; pressed twice it still goes to the session. The log has `key_clash` with `by` (`tmux`, `herdr`, `terminal` with `app`, `macos`), `key`, `fallback`, and `asked` or `answered`; then `key_clash_ask` when the question shows and `key_clash_answer` (`answer`: `fallback` or `own`) when you answer.

**Inside herdr**, two more things:
- **herdr's variables stay outside.** herdr marks its panes (`HERDR_ENV`, `HERDR_PANE_ID`, `HERDR_TAB_ID`, `HERDR_WORKSPACE_ID`, `HERDR_SOCKET_PATH`), and herdr's own Claude Code hooks report to the pane named there. None of them reach Kiko's tmux, the app or a session, so sessions in Kiko's window never report as the herdr pane you ran `kiko` in (herdr issues #2134 and #2135).
- **Right-clicks.** herdr keeps the right mouse button for itself by default. `kiko` asks it once to pass this pane's on (`herdr pane input --current --right-click pane`), so the list's right-click menus work. A herdr that can't (0.8.0 has no `pane input`) gets a note under the list saying how: update herdr and run that command, or hold herdr's passthrough key (`ui.right_click_passthrough_modifier`) as you right-click.

### Before you start
- tmux (a checkout; an installed copy brings its own): `tmux -V` should print 3.x (3.3 or newer; 3.8 for the classic look; 3.8 is installed from Homebrew). If it's missing: `brew install tmux`.
- **Installing a release instead** (`curl -fsSL https://kiko.sh | sh`, or `sh install.sh` with `KIKO_RELEASES_URL`: `RELEASING.md`): it checks first for a coding agent (Claude Code, Codex, OpenCode or T3 Code) and, with none, offers to install Claude Code with its own installer; checks that the download is signed by Kiko's developer; then downloads, puts `~/.local/bin` on your PATH in your shell's startup file when it isn't (one marked line, said; `kiko uninstall` takes it out) and runs `kiko setup`. Open a new terminal after it to use `kiko`.
- A fresh clone needs `pnpm install` once (`CONTRIBUTING.md`, "What you need"); after that, a change here added no packages.

### What to restart
- **The Kiko app**: quit it if it's running (Ctrl+Space `q` in the window). The window's menu and keys changed (n/p/l/c/d, ↑ ↓ move the highlight; the session shown's r/i/x and the graceful Close, 2026-10-29): a window from before shows the old menu until the app restarts. The menus' new colours are set by `kiko` as it opens the window, so run it once after updating. From now on `kiko` (or `pnpm start`) starts it, in the window: it no longer runs in a terminal of its own.
- **Kiko's tmux, if a session still runs there from before:** nothing to do. Its server keeps the config it started with, so `kiko` sets what the window needs itself; only the rest of the config (below) needs a reload.
- Nothing else. The status line and `~/.claude/settings.json` don't change, and sessions already running carry on as before. The hook script (`hooks/claude-code-hook.mjs`) now also sends Claude Code's pid; each hook runs it afresh, so nothing to restart for it.

### Putting `kiko-dev` on your PATH
A checkout runs as **Kiko Dev** (see "Developing": its own settings, keys, tmux server and socket), so its command is `kiko-dev`, and `kiko` is left for an installed release. Pick one; nothing was installed for you:
- **`pnpm link:dev`** in the repo: links `~/.local/bin/kiko-dev` to this checkout's `bin/kiko-dev` (`~/.local/bin` must be on your PATH).
- **An alias** in `~/.zshrc`: `alias kiko-dev="$HOME/git/kiko/bin/kiko-dev"`
- **`pnpm link --global`** in the repo (package.json's `bin` has both; needs pnpm's global bin folder on your PATH; not tried).

Any of them runs whatever branch is checked out in that folder. It needs Node 24 on your PATH. Where these steps say `kiko`, a checkout's is `kiko-dev` (and `tmux -L kiko` is `tmux -L kiko-dev`).

## Your API keys: the Keychain (2026-10-31)
Kiko's own calls use up to four keys: **OpenRouter** (the one key: every model and the classifier), **Anthropic** (optional: Haiku billed to Anthropic directly), **Deepgram** (only with Deepgram speech-to-text) and **Cartesia** (only with the Cartesia voice). They're kept in the macOS Keychain, never in a file.

- **One key is enough:** with nothing chosen, Kiko uses the Pocket voice, Apple's speech recognition and Claude Haiku through OpenRouter; with a Cartesia, Deepgram or Anthropic key it uses Cartesia, Deepgram or Haiku on Anthropic instead. In settings, an engine or model whose key is missing says "· needs a key", and picking it asks for that key right there (checked, then saved; Esc leaves the setting as it was). A choice whose key has gone missing doesn't stop the app: a free one stands in, and the app says so once as it starts ("No Cartesia key, so the Pocket voice is speaking. Add one in Settings → Keys."). Only with neither an OpenRouter nor an Anthropic key does it stop, saying `kiko keys set openrouter`.

- **Enter them in one place:** settings → **Keys** (Ctrl+Space `s`), a row per key that what you've chosen can use, or `kiko keys set openrouter` in a terminal (it asks for the key without showing it; `pbpaste | kiko keys set openrouter` works too). Each key is checked first with a cheap call to its provider ("✓ OpenRouter key works", or what the provider said); offline, it says it couldn't check and asks whether to save it anyway.
- **See where each comes from:** `kiko keys` lists them, set or not, from the environment, `.env` or the Keychain, by their last four characters only. The Keys rows say the same.
- **Take one out:** `kiko keys remove openrouter` (it asks first), or Keys → the key → Remove from the Keychain.
- **`.env` still works, and wins:** a key in your environment or `.env` is used over the Keychain's (for development). At start the app fills in only the keys missing from both, from the Keychain. Moving yours over: enter each one in Keys (or `kiko keys set …`), then take it out of `.env` yourself; `kiko keys` then says "Keychain" for it.
- **The first time** the app (or `kiko keys`) reads the Keychain it builds its helper (`native/macos/keychain.swift`, signed with your developer identity if this Mac has one). macOS may ask once whether "keychain" may use your confidential information: Always Allow. See ARCHITECTURE.md ("The keys") for why it can ask again.
- `KIKO_KEYCHAIN=off` turns the Keychain off: keys only from the environment and `.env`, as before.

## Connecting your agents (branch `agents-card`, 2026-10-30)

Kiko hears a session through its agent's hooks. The first time you run plain `kiko`, it looks for every agent it supports on your Mac and asks once, in a card drawn like the key clash question:
```
╭──────────────────── Agents ────────────────────╮
│ Which coding agents should Kiko talk to?     │
│ [x] Claude Code   adds hooks to ~/.claude/settings.json
│ [x] Codex         adds hooks to ~/.codex/hooks.json
│ [x] T3 Code       not running
│ ─────────────────────────────────────────────── │
│ Space ticks · Enter goes on · Esc later         │
╰─────────────────────────────────────────────────╯
```
- **Found:** Claude Code (`claude` on your PATH, or `~/.claude`), Codex (`codex`, or `~/.codex`), OpenCode (`opencode` on your PATH, or `~/.opencode/bin`; it needs no hooks either: ticked, connecting it is Kiko's yes to listening to its background service, kept in Kiko's settings), T3 Code (its CLI in `~/.t3`; it needs no hooks: ticked, nothing is written and Kiko connects to it while it runs; unticked, Kiko leaves it alone, never connecting or listing its threads, until settings → Agents → T3 Code → Turn on). In the card, agents already connected show as connected and aren't asked about. A new agent (Pi) will be one more entry in `src/agents/setup.ts`.
- **First-run setup (`kiko setup`)** asks "Which coding agents should Kiko talk to?" with every supported agent found as a box (2026-11-01): the ones to connect ticked, the connected ones ticked too (unticking one takes Kiko's hooks out, backed up first, as Disconnect does), T3 Code ticked; "Pick at least one. Space ticks, Enter goes on." Enter with none ticked isn't taken (Clack's "Please select at least one option."); Esc skips the step. The supported agents not on this Mac are one line above: "Also works with: OpenCode (not installed here)."
- **Space** ticks or unticks the line chosen, **↑ ↓** move, **Enter** connects the ticked ones, **Esc** is "later". It's a popup over the window: nothing waits on it, and the window works around it. After a key clash question, it comes once that one is answered or let go.
- **Connecting** merges Kiko's entries into the agent's file next to yours (each of yours kept, in its place), after a backup next to it (`settings.json.kiko-backup-<when>`), written whole and moved in place. A file that isn't JSON is left alone, and said. Claude Code: `hooks/claude-code-hook.mjs` on Stop, PermissionRequest, SessionStart, SessionEnd, UserPromptSubmit, PermissionDenied and PreToolUse (the safety gate's, for shell commands and MCP tools only); sessions already open pick them up when restarted. Codex: its own installer (`kiko setup codex`'s); Codex asks you to trust the hooks once, at its next start ("Hooks need review"). Under the list, a line says what happened.
- **The status line isn't added.** `statusline/kiko-status.mjs` wraps your own `statusLine` command, so adding it means rewriting yours; Kiko never touches your `statusLine`. To use it, set it by hand (its header says how).
- **Remembered:** "later", or an agent you unticked, is kept in the settings (`agentAnswers`), so the card doesn't come back every start. An agent found later that isn't connected and wasn't answered about (Codex installed next month) gets the card once.
- **Needs repair:** hooks that are there but broken (the hook's script gone because the repo moved; Stop or PermissionRequest missing; for Codex, an event missing) show as "needs repair", and Enter fixes them: Kiko's entries are pointed at this checkout's hook, in place, and the missing ones added. A hook pointing at another checkout that still exists counts as connected. Skipped on the card, it's said at each start instead (and so is "no agent is connected").
- **Kept up to date** (2026-10-30): when a Kiko update adds a hook event (Claude Code's PermissionDenied was the first), the app adds it at start to each agent you've connected already, the same way as Connect (next to yours, after a backup), and says so once: "Added Kiko's new Claude Code hook (PermissionDenied)." An entry of Kiko's whose matcher or timeout changed (Codex's PreToolUse, widened for the safety gate, 2026-11-02) is brought up to date the same way: "Updated Kiko's Codex hook (PreToolUse): Codex asks you to trust it again at its next start." Only Kiko's own entries are ever added; an agent you haven't connected, or said no to, is never touched; a file that isn't JSON is left alone; one whose hook moved waits for you to repair it, as before. An event of Kiko's you take out of the file by hand stays out: Kiko keeps which events each file has been given (`hooksKnown` in its settings), and only adds ones it never gave it. `kiko` itself (the command line) doesn't do this; the app it starts does.
- **Settings → Agents** (the first section): one row per supported agent with where it stands (Connected, Not connected, Not installed, Needs repair, Connects by itself, Off), and Connect, Disconnect, Repair (and "Add the rest" for Claude Code's optional hooks); for T3 Code, Turn off and Turn on (at once: its connection closed or opened, its threads off or back on the list). Disconnect takes out only Kiko's entries, after a backup, and the card won't offer it again. This is where to go after saying later.
- **From a terminal:** `kiko setup claude`, `kiko setup codex` or `kiko setup opencode`: it says what it adds and where, and asks y/N. Plain `kiko setup` is first-run setup, whose first screen is the same list (ticked). `kiko uninstall [claude|codex]` takes Kiko's entries out the same way.
- In `logs/latest.jsonl`: `agents_card` (at start: each agent's state, what was offered, where the card showed), `agents_card_shown`, `agents_card_answer`, `agent_connected` / `agent_repaired` (the file, the events, whether it was backed up), `agent_disconnected`, `agent_failed`, `hooks_upgraded` (at start: the agent, the events added, the file and its backup), `hooks_upgrade_skipped` / `hooks_upgrade_failed` (why nothing was added).

## T3 Code (2026-10-29; on a par with a Claude Code session in Ghostty since `t3-parity`)

Kiko also talks to [T3 Code](https://github.com/pingdotgg/t3code)'s threads, alongside your Claude Code sessions. Claude Code stays the main agent: new sessions still start in Claude Code unless you ask for a T3 thread, and everything above is unchanged. When T3 Code isn't running, Kiko works exactly as before.

**What works**
- **Its threads are listed** with your sessions: each thread that isn't archived or settled, by its title, in its project's folder (its worktree if it has one). They show busy while a run goes, and "needs you" while one waits on a permission or a question.
- **You hear what it says.** When a run completes, Kiko reads the thread's last reply and announces it (or reads it out), as for a Claude Code session. There's no reply window: T3 can't hold a run for you.
- **You can reply, at any moment.** Say something to the thread, by name or right after it spoke: your words go to it as a new message, as if typed in T3 ("→ <thread> (T3 Code)"). While a run is going, T3 decides whether they steer it or wait for it (as its own message box does).
- **Its permissions are asked here,** as a Claude Code session's are, when the thread is approval-required and wants to run a command, change or read a file, or use a tool: said out loud ("Pixie login wants to run: npm test. Allow?"), on the Mac's card with its keys (`y` allow, `a` allow for the rest of the session, `n` no), and on the phone (Allow / Deny). Your answer goes back to T3 and the run goes on; "no" tells the agent why. Not answered in time, it waits in T3 Code ("no answer; the prompt is waiting in T3 Code"); answered in T3 meanwhile, Kiko stops asking.
- **Claude's questions** (AskUserQuestion, in a T3 thread) are asked one at a time by voice and shown with their options on the phone, as a Claude Code session's are; the answers go back to T3.
- **Stop and rename** by voice ("stop pixie login", "rename pixie login to login cookies") and from the menus (right-click, `r` in the list, Interrupt, Rename…): done through T3's server, at any moment (a rename doesn't wait for the run to end). The new title shows in T3 and in Kiko's list.
- **Close is archive:** a thread isn't a process, so its menu's `x` is "Archive in T3 Code…", asked first ("Archive Pixie login in T3 Code? It leaves the list; T3 can bring it back."). A run that's going is stopped first (T3 won't archive a running thread). It can be restored in T3.
- **Its conversation in the Kiko window:** click it (or Enter) and the stage shows it read-only, as an outside Claude Code session's is ("in T3 Code" in its header), kept up to date while it's shown. With it shown, the Ctrl+Space menu has Rename…, Interrupt and Archive for it too.
- **A request Kiko can't read** (one with nothing saying what it asks, an MCP elicitation T3 answers by message, a provider that can no longer take the answer) is said once as before, "<thread> in T3 is waiting for you in T3 Code", and answered in T3.
- **New threads by voice or the phone:** "start a T3 thread in pixie and fix the login bug" makes the thread in T3 Code, in the T3 project pixie, with that as its first message (no message: an empty thread, "New thread"), on T3's default model, or Codex's or Claude's when you say "on Codex" or "with Claude". It's listed with your sessions, Kiko says "Started a T3 Code thread in pixie.", and your next words go to it. The project has to be one of T3's ("tideline isn't a project in T3 Code yet. Add it in T3 Code first."); with none named and several in T3, Kiko asks you to name one. T3's window isn't brought forward. In the Kiko window, `+ new session` in a folder that's a T3 project offers T3 Code beside your other agents while T3 runs. **T3 Code not running:** the session starts in a terminal instead, as any new session would (your default agent, or the one you named), and Kiko says so: "T3 Code isn't open, so I'm starting it in Claude Code."

**Not yet:** bringing T3's window forward, closing by voice (not there for Claude Code sessions either). From the phone, a thread's ⋯ menu archives it as the window's Close does.

**Setup:** none. Install T3 Code (the desktop app, or `t3` from npm) and run it. Kiko finds its server on `127.0.0.1` (the port in `~/.t3/userdata/server-runtime.json`, else 3773). At start, and when T3 starts or restarts later, it mints a short-lived token with T3's own CLI (`~/.t3/bin/t3 auth session issue --scope orchestration:read --scope orchestration:operate --ttl 15m --json`): no pairing, nothing to approve. `orchestration:operate` is all that answering, stopping, renaming and archiving need too (T3 checks it per method, for `dispatchCommand`). The token stays in memory only (never logged, printed or saved), is renewed before it runs out, and is revoked when Kiko quits.

**Versions:** Kiko checks T3's orchestration protocol, not its app version (T3 updates itself several times a day). Supported: **protocol 2** (tested against T3 Code 0.1.5's source). If T3 updates to another protocol, Kiko says once "T3 Code updated in a way this Kiko doesn't know yet; voice control of T3 is off until Kiko updates." and carries on without T3. The log has `t3_connect {protocol, ok, why}` each time that changes.

A Codex session's hooks run from its first message: open Codex and send one, and it shows in Kiko. If a Codex turn runs and no hook reaches Kiko, Codex shows as "needs repair" in settings → Agents and Kiko says so once (`hooks_silent` in its log), with what to check. The hook keeps a small record of each running Codex session for Kiko in `~/.config/kiko/codex-sessions/` (its pid, folder and rollout; Codex has none of its own), whether Kiko runs or not.

**Logs:** `codex_daemon {ok, why}` when Kiko's connection to Codex's daemon comes or goes, `codex_command {method, threadId, ok}` for a rename or interrupt through it, and the same events as Claude Code's, with `"agent":"codex"`: `hook_stop`, `hook_permission`, `hook_answer`, `session_started`, `session_ended`, `prompt_submitted` (for either agent with `voice: true` when the prompt was your dictated words the app had typed in, and its hook told the agent so: `ARCHITECTURE.md`, "The agent is told your words were spoken"), plus `session_interrupted` (its Interrupt hook), `codex_question`, `session_adopted` (a pane running `codex` in Kiko's tmux, listed from its pane), `hooks_silent` (a Codex turn no hook told of), `session_at_prompt` and `held_typed` (a session opened without a prompt, its first words typed in once its composer shows), and `session_open` with `agent`.

## OpenCode (2026-10-30, branch `opencode-adapter`; built against a fake OpenCode service, not yet tried with the real one)

Kiko also talks to [OpenCode](https://github.com/anomalyco/opencode) sessions, in Ghostty or any other terminal and in Kiko's tmux. **OpenCode 2.0 or later; checked against 2.0.32** (its source, and its real background service's API with read-only requests). OpenCode has no hooks: every OpenCode TUI is a client of one background service on your Mac (an HTTP API with an event stream), and Kiko is one more client of it. So nothing of OpenCode's is changed: no config, no plugin, nothing for you to trust or review in OpenCode. As with Codex, once OpenCode is connected a new session starts in the agent you name, else the one preselected, and the window asks which (`kiko opencode` preselects OpenCode for its run).

**What works**
- **Listed as soon as it has a session,** wherever it runs (Ghostty, Warp, iTerm, Kiko's tmux): a session is listed only while an OpenCode TUI that made, used or looked at it since it started runs in its folder. OpenCode's service keeps every session after its TUI quits, but Kiko doesn't list one no TUI shows, and never sends it words (they show as not sent, and why): the service would run a turn for it that nobody sees. OpenCode makes a session at its first message, so a TUI opened with nothing typed has none: in Kiko's tmux its pane is listed all the same (as Codex's is), elsewhere it shows from its first message. Listed by its title (yours, from Ctrl+R or Kiko's Rename, or OpenCode's own after the first message), "busy", "idle" or "needs you" as Claude Code's are, on the Mac and the phone (the phone shows "OpenCode" beside it). A TUI you quit takes its sessions off the list (the Mac's, the window's and the phone's) within a second or so; a reply window or permission held for one is let go.
- **Heard:** when a turn ends, its last reply is summarised and read out, with a reply window as for Claude Code. OpenCode doesn't wait for anyone after a turn, so a reply said there goes to it as a new message through its service (shown in its TUI as if typed). Typing in its TUI first closes the reply window.
- **Replied to at any moment:** in Kiko's tmux, typed into its pane (found by its TUI's process); anywhere else, sent as a new message through its service: no keys, no window to find, and a draft in its prompt is left alone. Mid-turn, OpenCode queues it for after the turn.
- **Permissions** (a command, an edit, a fetch, an MCP tool…): said out loud, on the Mac's card and on the phone; the answer goes back through its service. "Always" is offered when OpenCode says what it would save (as its own "Always allow"), and a no tells it why. One answered in its TUI first closes here, as answered there (the log has OpenCode's reply: once, always or reject); one dropped with Esc in its TUI (OpenCode says nothing of that ask) closes as its turn is interrupted or the session goes idle. Not answered, it's left asking in its TUI.
- **Its questions** (its question tool): asked by voice and on the phone as Claude Code's are, and answered back through its service. A form from an MCP server is said once, to answer in its window.
- **Its name, both ways:** renaming it from Kiko (the menus, `r`, "rename <session> to …") sets its title through the service, wherever it runs, at any moment: its TUI shows it at once. Ctrl+R in OpenCode shows here at once.
- **Its conversation on the phone and in the window:** its messages through the service, written as a transcript Kiko follows (your messages and its replies, each reply once it's written in full: no steps or diffs yet), live while the chat is open, through a moment the service drops.
- **Interrupt,** by voice ("stop <session>") and from the menus, through its service, wherever it runs (no Escape typed).
- **Close:** `/exit` typed in Kiko's tmux; elsewhere a SIGHUP to its TUI after the same checks as Claude Code's (still the process seen in front in its folder, started when it was, and `opencode`), which OpenCode takes as its terminal closing: it puts the terminal back and quits.
- **Started from Kiko:** "start an OpenCode session in pixie" opens `opencode` in Kiko's tmux, in the window (`opencode --prompt '<words>'` with a first message, which OpenCode sends as it opens). A name ("named docs", or the phone's New session **Name**) is given through its service once it's listed, over the title OpenCode makes up from the first message. Opened with nothing to do, it's shown as ready once its prompt is up, and the first thing you say to it is typed in then. `kiko opencode [args…]` starts one by hand, as `kiko claude` does, and preselects OpenCode for new sessions that run.

**Not possible, or not yet**
- **Several tabs in one TUI** (OpenCode 2's tabs): each tab's session used since the TUI opened is listed (a tab you close there leaves the list), but only the one used last is taken to be in front (its TUI's process: shown in the window, closed with SIGHUP). The others take words, renames, interrupts and answers through the service, but aren't closed from Kiko (it would close the whole TUI). Two TUIs in one folder: the same, neither closed from Kiko.
- **An old session reopened** in a TUI (its session list, or a tab a new TUI shows again from its last run) shows once it's used (a message, or looked at after it finished): OpenCode doesn't say which session a TUI shows, so one it only shows isn't taken to be open. Two open sessions with the same title (OpenCode titles many "Greeting") are told apart only by when they were last active: rename one (Ctrl+R there, or Kiko's Rename) to tell them apart by voice.
- **OpenCode 1.x** has no background service: settings → Agents says to update it.
- **Unverified with the real OpenCode:** its SIGHUP quit, its prompt read as ready (`Ask anything…`), `/exit` typed into it, and Escape (unused: interrupts go through the service). All are from its source.

**Setup:** tick OpenCode on the first-run card, or Connect it under settings → Agents, or run `kiko setup opencode`. That's Kiko's yes to listening to OpenCode's background service: it's kept in Kiko's settings (`linkedAgents`), and Kiko then reads the service's address and password from the service's own file (`~/.local/state/opencode/service.json`, 0600), only to talk to it on this Mac (never on a command line, never logged). Nothing to restart: open any OpenCode session. `kiko uninstall opencode` (or Disconnect) stops it. Not connected, Kiko never reads that file.

**Logs:** `opencode_service {ok, why}` when Kiko's connection to the service comes or goes, `opencode_command {method, sessionId, ok, why}` for a reply, rename, interrupt or message through it, `opencode_turn`, `opencode_permission`, `opencode_questions`, `opencode_reply` (an answer sent back), `prompt_submitted` with `"agent":"opencode"`, `session_adopted` (a pane running `opencode` in Kiko's tmux, listed from its pane), and `session_open` with `agent`.

## Developing
How to run, test and change it: `CONTRIBUTING.md`; how it's put together: `ARCHITECTURE.md`; releases: `RELEASING.md`; renaming the app: the name comes from `src/core/name.ts` (that file lists the rest).
- `pnpm check`: typecheck, lint and format check, and the unit tests (`pnpm test`, `tests/unit/`, fast). They never speak: `KIKO_SPEECH_LIVE=1` adds the real speech (`say` and the Apple recognizer) in `tests/unit/remote/opus.test.ts`.
- `pnpm test:live`: the live tests (`tests/live/`: real tmux servers, the real `bin/kiko`, an install), one file at a time; `pnpm test:all` runs both.
- **A real `claude` in a test or a check by hand:** only through `scripts/isolated-claude.sh`, with a config folder of its own (`CLAUDE_CONFIG_DIR`), so it never shows in your Kiko or `claude agents`, nor leaves anything in `~/.claude` (CONTRIBUTING.md, "Checks").
- `pnpm test:app`: the whole app on stubs (`tests/harness/`, about 6 minutes, so not in `pnpm check`); `pnpm check:full` runs `pnpm check` and then it, and is what to run before merging a change to `src/`. `pnpm test` checks that the harness's stubs still export what the app imports from the modules they stand in for. `pnpm test:e2e`: install to uninstall, end to end (slow).
- **Evals** (real models: they need API keys and cost a little): `pnpm eval:routing` (`tests/eval/run.ts`, the cases in `tests/eval/cases.ts`, written from scratch, plus the private ones made from real speech in `tests/eval/private/` when that folder is there: it's left out of the public repo) and `pnpm eval:summary` (`tests/eval/summary.ts`, the spoken summaries). The summary eval's real cases are your own replies, taken from `logs/` (`--extract --logs logs`), so they're never committed: keep them in `private-evals/` (git-ignored) or any folder outside the repo, and pass it as `--data` (`pnpm eval:summary --data private-evals --report`). Without `--data` it runs on `tests/eval/sample/`, a small made-up set of the same shape, and `--extract` refuses to write there.
- **Relay eval** (`pnpm eval:relay`, `tests/eval/relay/`): what arrives in a session when you name it, relay through Kiko ("tell Bobby to …") or reply to the one waiting. ~225 cases (`cases.ts`, a stored train/validation/test split each; the ones made from real speech, with their splits and references, are private, in `tests/eval/private/`, so the public repo runs the ~190 constructed ones) run through `decide()` as the routing eval does, then two judges: hard checks in code (`checks.ts`: the right session, the direction gone, details and negations kept, nothing added, replies as said) against a committed, hand-reviewed reference that Opus 5.5 wrote (`reference.json`, `--build-reference`), and Opus 5.5 itself (`judge.ts`, checked against hand-labelled outcomes with `--calibrate`). `--list` (no network), `--split`, `--tag`, `--case`, `--repeat`, `--variant <module>` (a relay strategy to compare: `variant.ts`). Opus 5.5 (judge and reference) runs on your Claude plan by default: `--judge plan` (`KIKO_EVAL_JUDGE`) is headless `claude -p` on your Claude Code login, $0, concurrency 4 (`plan.ts`; it stops with a clear line if `claude` is missing or not logged in, never falling back); `--judge api` pays with `ANTHROPIC_API_KEY`. The engine under test always runs on the API. `--rejudge <run>.json` judges an earlier run's outcomes again. Each run writes a `.summary.json` to `tests/eval/results/` for comparing runs. A case's `alsoOk` lists other right outcomes (`null`: asking back, sending nothing); the judge reads only the reference's notes, so a case where asking back is right says so there too (the misheard names `stt-kiko-death`, `stt-taxi-log`, `stt-pixy`: "Did you mean rowan?" passes, 2026-11-07). In a worktree: `node --env-file=<main checkout>/.env tests/eval/relay/run.ts`.
- Developer tools (`pnpm smoke`, `pnpm support`, `pnpm shadow:report`, the benchmarks in `perf/`, the release build) are in `scripts/`.

### Kiko Dev: a checkout beside an installed release
A checkout runs as **Kiko Dev**, an installed copy as **Kiko**, and the two share nothing, so you can develop in one and test the release on the same Mac (ARCHITECTURE.md, "Two flavours"):
- **Kiko Dev** (`kiko-dev`, `pnpm start`, `bin/kiko-dev`): the window says "Kiko Dev", the phone lists "Kiko Dev on <your Mac>"; settings in `~/.config/kiko-dev/`, keys under the Keychain's `sh.kiko.dev.keys`, `tmux -L kiko-dev`, `/tmp/kiko-dev.sock`, the phone on port 7334, logs in the repo's `logs/`. The name you call it (the wake word) is still your setting, Kiko by default.
- **The release** (`kiko`, installed by `install.sh`): every real name (`~/.config/kiko/`, `sh.kiko.keys`, `-L kiko`, `/tmp/kiko.sock`, port 7333, logs in `~/.local/state/kiko/`).
- **One at a time:** starting one while the other runs says "Kiko (the release) is running; quit it first" (or the other way round) and starts nothing: both want the talk key and the mic.
- **Hooks:** each one's entries in `~/.claude/settings.json` and `~/.codex/hooks.json` reach only its own app; both can be there, and the one whose app isn't running does nothing. Each `kiko setup`/upgrade/uninstall touches only its own. The status line follows the copy its script is in: point `statusLine` at the checkout's `statusline/kiko-status.mjs` for Kiko Dev's, at the release's (`~/.local/share/kiko/current/kiko hook ~/.local/share/kiko/current/statusline/kiko-status.mjs -- …`) for the release's.
- **The first start of Kiko Dev** copies `~/.config/kiko` into `~/.config/kiko-dev` (the original stays) and your API keys into its own Keychain service, once, and says so.
- **Its permissions are Kiko Dev's** (2026-11-02; ARCHITECTURE.md, "The helper app"): the mic, the talk key and Apple's speech-to-text run in `native/macos/.build/Kiko Dev.app` (bundle id `sh.kiko.dev.helper`), which the checkout builds on first use and again only when `native/macos/app/*.swift`, the four helpers' sources or `scripts/build-helper-app.sh` change (a few seconds), and starts in the background. macOS asks for "Kiko Dev", once; the release's "Kiko" is another app and is asked for separately. **Signing:** with your developer identity when the Mac has one (`security find-identity -v -p codesigning`: Developer ID Application first, then Apple Development; `KIKO_SIGN_IDENTITY` overrides), so a rebuild keeps the grants; ad hoc (`-`, or no identity), macOS ties them to the binary's hash and asks again after every rebuild. A worktree builds its own copy at its own path with the same bundle id: Launch Services opens the one `kiko` names, and the grants are shared (same id and team). `KIKO_HELPER_APP=off` runs the helpers as `kiko`'s children instead (the terminal's permissions, as before); the log's `helper_app` line says which was used and why.
- **Tests:** `KIKO_FLAVOUR=release` or `=dev` forces a flavour (unit tests always run as the checkout, Kiko Dev).

### What the user README leaves out (moved here 2026-11-01)
`README.md` was cut down to the essentials on 2026-11-01. The details it had, kept here as they were:
- **Versions:** Codex CLI 0.153 or later, OpenCode 2.0 or later. Intel builds are made but less tested.
- **The install script:** offers to install Claude Code when no agent is found; downloads the build for the Mac's chip and checks it; installs in `~/.local/share/kiko/` and links `~/.local/bin/kiko`; adds `~/.local/bin` to the PATH when it's missing (one marked line in `~/.zshrc` or the shell's startup file); starts downloading Pocket, Kiko's free voice (about 1 GB), in the background; runs `kiko setup`. If it says so, open a new terminal before running `kiko`.
- **Setup's steps:** agents (hooks added to each agent's settings file, backed up first, the user's own hooks kept), the OpenRouter key (checked, then kept in the Keychain), the microphone (macOS asks, then a test), the talk key (Right Option or another; needs Input Monitoring), the name you call it (Kiko by default), hello (so you know the sound works), then what to try, and Kiko opens. Started from a different terminal app, macOS asks for the permissions again. A step done before whose permission is gone now (the helper app renamed, `tccutil reset`, turned off) is asked again, with a line saying so, and taken out of `setupDone` (`setup_start`'s `stale`); the name and hello never are. **The terms** (`src/core/terms.ts`): one dim line before the first step, "By continuing, you agree to Kiko's Terms (kiko.sh/terms) and Privacy Policy (kiko.sh/privacy).", once per terms version: going on past that step (answered or skipped; not Ctrl+C twice) keeps `termsAccepted` (`{ version, at }`, the version being TERMS.md's effective date, `TERMS_DATE`; `setup_terms` in the log). A new effective date: "Kiko's Terms changed on <date>: kiko.sh/terms" once instead, in setup or at the app's start (`terms_changed`), never a question. Change `TERMS_DATE` with TERMS.md's date (a test checks they match). Signing in says "By signing in, …" by the code (`kiko login`, setup), the trial "By starting the free trial, …", Kiko Pro's plan question "By subscribing, you agree to the Terms, including Kiko Pro's: kiko.sh/terms". At the app's start, a microphone not allowed is said and stays on the window's line until it is (`mic_unallowed`, then `mic_allowed`), as the talk key's Input Monitoring is.
- **Everyday:** sessions started elsewhere (plain `claude` in another terminal, the Claude desktop app, T3 Code) are listed and heard, and answered when they speak. The menu's `d` hides the window; the **☰ Kiko** button opens the menu too. More to say: "tell clipkit the build is green, open a PR", "more about the failing tests", "Kiko, which sessions are working?" (words that start with its name are for Kiko itself). **Settings → Control → Voice can → Everything** also lets your voice start, stop and rename sessions. With macOS 26, **Settings → Listening → Listen** goes hands-free ("Kiko, …").
- **Updates:** checked once a day and downloaded in the background; the window's header says when one is ready, and **Settings → Updates → Restart now** switches to it. **Settings → Updates → Automatic updates** off: Kiko only says a new version is out.
- **Uninstall:** quit Kiko first (Ctrl+Space `q`). It removes Kiko's hooks from each agent's settings file (only Kiko's, backed up first), `~/.config/kiko/`, `~/.local/share/kiko/` (every version, its tmux, the Pocket voice), `~/.local/bin/kiko`, the installer's PATH line and its Keychain keys; it asks about the logs separately. It leaves `~/Kiko/scratch`, the agents' backups and any session still open.
- **More troubleshooting:**
  - "Almost no sound came in": pick the mic in **Settings → Listening → Microphone** and try **Test microphone**. Another talk key: **Settings → Listening → Push-to-talk key**.
  - "Apple speech recognition couldn't start": it needs macOS 26; pick Deepgram in **Settings → Listening → Speech recognition** (it asks for a Deepgram key).
  - `kiko keys` shows which keys are set, by their last four characters only.
  - Codex asks once to trust the new hooks ("Hooks need review"): "Trust all and continue", and quit every Codex so the next one starts fresh. T3 Code shows up while it's running.
  - Ctrl+Space doesn't open the menu: your own tmux, herdr, Warp or macOS's input-source shortcut may take it first; Kiko uses Ctrl+\ that run and asks whether to keep it. Pick your own in **Settings → The Kiko window → Menu key**.
  - "Kiko's own tmux is missing from its folder": run the install line again.
  - Logs: one file per run, `latest.jsonl` the current one.
- **Privacy, in short:** voice to text on the Mac by default, and Kiko's voice runs on the Mac. The text of what you say, plus sessions' names and recent replies, goes to OpenRouter; Deepgram and Cartesia only with their keys. No analytics, no telemetry (`PRIVACY.md`).
