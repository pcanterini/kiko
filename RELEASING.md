# Releasing Kiko

How a release is cut, and what people's Macs get. One command does it: `pnpm ship [version]` (below, "Shipping one"). Releases are served from kiko.sh (an R2 bucket, `kiko-releases`, behind the site's Worker). 0.2.0 (2026-11-01) to 2.0.x went out under the old name, from fala.sh (`fala-releases`); the Kiko bucket, domain and site are made before the first Kiko release.

## What a release is

One tarball per Mac chip, `kiko-<version>-darwin-<arch>.tar.gz` (arm64, x64), unpacking to `kiko-<version>/`:

| | |
|---|---|
| `kiko` | the whole app as one executable (Bun's `--compile` of `src/main.ts`; no Node needed). It is also each of the app's own programs (`kiko _run app`…) and runs the agents' hooks (`kiko hook <script>`) |
| `Kiko.app` | the helper app (ARCHITECTURE.md, "The helper app"): a background-only app holding the helpers that need a macOS permission (`mic`, `hotkey`, `speech` (macOS 26), `permissions`, in `Contents/Helpers/`), so macOS asks for and keeps the microphone and Input Monitoring for "Kiko", not the terminal. Built by `scripts/build-helper-app.sh`, per chip |
| `native/` | the other Swift helpers (`keychain`, `opus`, `player`, `presence`), prebuilt (macOS 13+) |
| `hooks/`, `statusline/` | the scripts Claude Code and Codex run, through `kiko hook`, and what they import beside them: `hooks/lib.mjs`, and the safety gate's rules (`hooks/guard.mjs`, `hooks/guard/`) |
| `pocket/` | Pocket TTS's server and setup script |
| `tmux/` | the window's `tmux.conf` and the empty pane's script |
| `bin/tmux` | tmux itself, built from source for that chip (`scripts/build-tmux.sh`): Kiko's own server (`-L kiko`) always runs it, so a Mac needs no tmux, no Homebrew |
| `terminfo/` | the `tmux-256color` entry its panes' programs need (macOS 13 has none; 14 and later do, and theirs is used first) |
| `LICENSE.md` | Kiko's own licence (MIT) |
| `THIRD_PARTY_NOTICES.md` | the licences of everything built in: Bun (the runtime inside `kiko`), every npm package compiled into `kiko`, tmux and what's built into it (tmux ISC, libevent BSD, utf8proc MIT, jemalloc BSD, the terminfo entry: ncurses, MIT-style), and code ported into Kiko's own source (today voice-glow's dither look, MIT). Made by the build, from what's in it (below, "Third-party notices") |

Beside them: a `.sha256` for each, and `latest.json`, the feed `install.sh` and `kiko update` read:

```json
{ "version": "0.1.1", "date": "2026-11-01", "notes": "one or two short lines",
  "assets": { "darwin-arm64": { "url": "…/kiko-0.1.1-darwin-arm64.tar.gz", "sha256": "…" }, "darwin-x64": { … } } }
```

## On a Mac it's installed to

- `~/.local/share/kiko/versions/<version>/`: the unpacked folder; the current one and the one before it are kept
- `~/.local/share/kiko/current` → `versions/<version>`, switched in one step (a link under a temporary name, renamed over the old one); `previous` → the one before
- Both `install.sh` and `kiko update` (`src/core/updates/`) keep this layout
- `~/.local/bin/kiko` → `current/kiko`; when `~/.local/bin` isn't on the PATH, `install.sh` adds one line to the shell's startup file (`~/.zshrc`; bash: the first of `~/.bash_profile`, `~/.bash_login`, `~/.profile`; fish: `~/.config/fish/conf.d/kiko.fish`), marked `# added by the Kiko installer (kiko uninstall removes this line)`, once; `kiko uninstall` takes out that line and no other
- Kiko's tmux server runs `current/bin/tmux` (`src/terminals/tmux/tmux.ts` `tmuxPath`), started with `TERMINFO_DIRS=/usr/share/terminfo:<current>/terminfo` (`tmuxEnv`), which every pane inherits. Your own tmux, if you have one, is never used for it (and never touched: a socket of its own); a checkout still uses the tmux on your PATH, or `KIKO_TMUX_BIN`
- The agents' hooks run `~/.local/share/kiko/current/kiko hook …/current/hooks/…`, so an update never breaks them
- Pocket's, all kept across updates: its venv `~/.local/share/kiko/pocket-venv`; `pocket-uv/` beside it, the uv `pocket/setup.sh` fetches when the Mac has no uv or Python 3.10+ (with the Python and cache any uv it runs keeps for Pocket); `pocket-hf/`, its model (HF_HOME). `kiko uninstall` takes them with the rest, and nothing of the user's (their uv, brew's Python, `~/.cache/huggingface`)
- The uv it fetches is pinned in `pocket/setup.sh` (`UV_VERSION` and a SHA-256 per chip, from the `.sha256` files the uv release publishes on GitHub): to move to a newer uv, change all three together
- Logs: `~/.local/state/kiko/logs/`; settings: `~/.config/kiko/` (as from a checkout)
- The invite (2026-11-05): `~/.local/share/kiko/install-token` (the install link's token) and `install-id` (a random id for this Mac), both mode 600, written by `install.sh` and read by every update (ARCHITECTURE.md, "Updates", the invite). `kiko update --token <token>` adds one to an install that has none
- A checkout (`bin/kiko-dev`, `pnpm start`) is **Kiko Dev**, beside it and sharing nothing: `~/.config/kiko-dev/`, `-L kiko-dev`, its own socket, Keychain service and phone port; its code, logs and Pocket in the repo, as before (`src/core/app-root.ts` and `name.ts` tell the two apart; ARCHITECTURE.md, "Two flavours")

Going back a version: `kiko update --rollback` (current and previous change places).

## Shipping one

```sh
pnpm ship 0.2.4 --notes "what's new, in a line"   # bump, commit, type check and test, build, publish; notarize after
pnpm ship --dry-run                                # everything local: type check and test, build, sign, check, pack; nothing leaves the Mac
pnpm ship 0.2.4 --full                             # notarize and wait for Gatekeeper first (after the launch)
pnpm release:status                                # how each release's notarization ended
pnpm release:notarize 0.2.4                        # notarize a published release again, by hand
```

`pnpm ship` (`scripts/ship/ship.ts`) runs from the main checkout and needs nothing improvised: it stops on a branch that isn't main, a tree that isn't clean (untracked files too), `.git/index.lock`, main behind origin, a version that isn't newer than the live feed's, or the website's checkout (`KIKO_SITE`) not on `main` (`KIKO_SITE_BRANCH`) and clean, or wrangler not logged in. With a version, it sets package.json's and commits it (`package.json: <version>`). It builds from a clean worktree at HEAD (in the temp folder, its dependencies installed, removed after) with tmux's build cache shared from the main checkout's `.cache/`, into `dist/<version>/`. Before building, it runs the type check and the unit tests in that worktree (`pnpm typecheck` and `pnpm test`, at once; a dry run too) and stops if either fails, saying what failed: tsc's errors, or each failing test's name, file and the first line of why (never the whole output). Nothing skips them (since 2026-11-12: before, a red tree could reach every install through `kiko update`). It prints the build's output, then each step's time and the total. It never prints credentials: wrangler and notarytool use the logins they have, and only their result lines are shown. Notes: `--notes` or `KIKO_RELEASE_NOTES` (otherwise "Kiko <version>").

### The fast path (the default until the public launch)

1. Checks (above), and how earlier releases' notarization ended: a rejected or stopped one is printed loudly, and it goes on.
2. Version bump, committed; the clean worktree.
3. The type check and the unit tests in it, at once: a line each with its time (`typecheck: passed (1.6s)`, `tests: 4585 of 4586 passed, 1 skipped (64.0s)`). Either failing stops the release here, before anything is built; the version bump stays committed, unpushed: fix, commit, `pnpm ship` again (without the version, or with it: it's package.json's already).
4. The smoke of the built executable (`pnpm smoke:binary`, `scripts/ship/smoke.ts`; from 2026-11-15): `release.sh` for this Mac's chip, signed ad hoc, into a temp folder, its tarball unpacked, and the executable run headless as it ships, under Bun (the tests run on Node): `--version`, `--help`, an unknown command, `_verify-files`, `keys`, `setup claude` without a terminal, and through `kiko hook` the voice hooks with no app, the quick checks' gate and the status line; each its exit code, output and stderr checked. Each run has a home, TMPDIR, tmux server name, socket, state and settings of its own, no Keychain, accounts off and a proxy that goes nowhere: never the app, the mic, a terminal, your tmux or your folders. About 13 s with tmux cached. A failure stops the release here, as the checks do (its folder kept, said where).
5. `release.sh` with `KIKO_NOTARIZE=later`: both chips built at once, signed, checked (the update requirement and identifiers, `_verify-files`, the relay vectors on this Bun, the notices, the .env/bunfig probe), packed at once. Nothing is sent to Apple, but the notary profile is checked first, so the notarizing after can't fail on it.
6. The tarballs checked against their `.sha256` and `latest.json`.
7. The built commit tagged `v<version>` (an annotated tag, the release's notes as its message; one already there is kept), then `git push origin main` and the tag.
8. Published: the tarballs and `.sha256` files to R2 (`kiko-releases`, at once; `Cache-Control: public, max-age=31536000, immutable`), then `latest.json` last (`no-cache`), so the feed never names a file that isn't there.
9. **Then** notarizing, in the background (a detached `scripts/signing/notarize.ts --dist dist/<version>`, its output in `dist/<version>/notary.log`): the tarballs unpacked, one zip to Apple, `notarytool submit --wait`, Apple's log checked to list every executable and Apple's ticket service to serve each (`notarized.ts`), then the Gatekeeper gate (`gatekeeper.ts`, up to 10 minutes). Each step is written to `dist/<version>/notary.json`; at the end a macOS notification says how it went.
10. The site, only if `install.sh` changed: copied into the site's `public/` (`scripts/sync-site.sh`'s job), committed and `main` pushed when the copy there differs, `pnpm exec wrangler deploy` when the one served differs.
11. Verified from outside (kiko.sh looked up at 1.1.1.1): `latest.json`'s version, each tarball downloaded and its SHA-256 equal to the feed's and its `.sha256`'s, and `install.sh` served at `/` and `/install.sh` equal to HEAD's. The feed and the tarballs are fetched with this Mac's invite token and install id when it has them (`~/.local/share/kiko/install-token`, sent from a header file, never on the command line), so verifying still works once the site's invite gate is on: give this Mac a token first (`kiko update --token <token>`, or its install link run again).

**Why notarizing can come after publishing.** People install with `curl | sh` and update with `kiko update`, which downloads in code: neither marks what it downloads as quarantined, so Gatekeeper's notarization check never runs on that path. What both check is the Developer ID signature, against `src/core/updates/verify.ts` `requirement` (team `YU89X2P36Z`, `sh.kiko.<file>`), and `_verify-files`, all checked before packing. A bare executable can't have its ticket stapled: its ticket lives on Apple's servers, looked up by the code's hash. So the files published are byte for byte the ones a notarize-first build would publish, and once Apple accepts them, a browser download of them passes Gatekeeper too. Until then (a minute or two, plus up to about 4 for Apple's ticket to reach Gatekeeper everywhere), only a browser download of a tarball would be refused.

**A rejection** (Apple says anything but Accepted; its log is saved as `dist/<version>/notary-log.json`) or a failure after (the ticket not served, Gatekeeper still refusing after 10 minutes, Apple not answering) never undoes the publish: everything installed by `curl | sh` and `kiko update` keeps working. It's printed loudly (a red block of `!!!`) by the next `pnpm ship` and by `pnpm release:status` (which exits 1), besides the notification. A rejection means the signing is wrong: fix it and ship a new version. A failure, or a background job that stopped (its process gone before it finished, e.g. the Mac restarted), can be run again: `pnpm release:notarize <version>`.

### The full path (from the public launch)

`pnpm ship --full` (or `KIKO_RELEASE=full`) keeps the old blocking order: build, sign, check, then notarize and wait for the Gatekeeper gate (`release.sh` with `KIKO_NOTARIZE=now`), only then pack, then publish, site, verify. Nothing runs in the background; `dist/<version>/notary.json` says it was notarized before packing. About 4 to 5 minutes more.

**When to switch:** at the public launch, when strangers may download a tarball with a browser, set `KIKO_RELEASE=full` for good (or make `full` the default in `scripts/ship/ship.ts` `parseArgs`). Until then the fast path is the default: everyone installs with `curl | sh`.

### Where the time goes (2026-11-02)

| | before (0.2.2, by hand) | `pnpm ship` fast | `--full` |
|---|---|---|---|
| checks, bump, worktree, `pnpm install` | 9 s | 4 s | 4 s |
| the type check and the unit tests (at once; from 2026-11-12) | none | about 65 s | about 65 s |
| the smoke of the built executable (one chip, ad hoc; from 2026-11-15) | none | about 13 s | about 13 s |
| tmux from source (a fresh worktree's empty `.cache/`) | 1 m 34 s | 0 (shared cache) | 0 |
| bundle, both chips, sign, check | 15 s (one chip after the other) | 11 s (at once) | 11 s |
| notarize (Apple) | about 40 s | in the background | about 40 s |
| Gatekeeper gate | 3 m 25 s | in the background | up to 4 m |
| pack | 5 s | 2 s (at once) | 2 s |
| upload, feed, deploy, verify from outside | about 1 m 30 s, typed by an agent | about 30 s (estimated: not run) | about 30 s |

The 0.2.2 release took about 8 minutes from the version bump to verified (and about 20 with an agent reading this file and improvising each step); the fast path's dry run took 22 s, so a real one should be under a minute and a half (its upload of about 85 MB and the outside download are the rest). The checks before building (2026-11-12) add about a minute to both.

### By hand

What `pnpm ship` runs, for trying one piece:

Needs bun 1.3.3 or newer (the executable; `bun upgrade`; built and tested with 1.4.4), Xcode or its Command Line Tools (`swiftc`, `cc`, `notarytool`), Node, the network (tmux's sources the first time; Apple's timestamp and notary services every time), and in the login keychain the Developer ID Application identity and a notarytool profile (below).

**A release never reads a .env file** (ARCHITECTURE.md, "Two flavours"). Bun's executables read a `.env` and a `bunfig.toml` from the folder they're started in unless built not to, so `scripts/release.sh` passes `--no-compile-autoload-dotenv --no-compile-autoload-bunfig` to `bun build --compile` (first in Bun 1.3.3; an older Bun stops the build with "needs Bun 1.3.3 or newer"), then starts the new executable (this Mac's chip) in a folder with a `bunfig.toml` and stops the build if it was read. Don't take the flags out.

**tmux** is built from source by `scripts/build-tmux.sh`, once per chip: tmux 3.8 with libevent 2.1.13-stable, utf8proc 2.12.0 and jemalloc 5.4.0 linked in statically (jemalloc because tmux's own configure insists on it on macOS: macOS's calloc crashed tmux servers, tmux issue 5385), macOS's ncurses linked dynamically; x64 is cross-compiled. Each source tarball is checked by its SHA-256 (pinned in the script; matched against Homebrew's formulae and GitHub's release digests when they were picked), and the result is cached in `.cache/tmux/` (ignored by git) by those versions, so only the first release build takes the extra minute or two. To move to a newer tmux: change the version and SHA-256 in the script (from two sources); bump `BUILD_REV` when only the flags change. The script refuses a binary that links anything but macOS's own libraries. A server keeps running the tmux it started with across updates (new clients come from the new version): fine while tmux's protocol version stays the same (it has for years); one that changes it needs a note telling people to quit their sessions' server (`tmux -L kiko kill-server`) after updating.

**Signing and notarization.** (The order below is the full path's; `pnpm ship`'s fast path notarizes the same files after publishing them: "Shipping one".) Everything that runs is signed with **Developer ID Application: Bald Cactus, LLC (YU89X2P36Z)** (the user's company's Apple team, the same as their other apps), with the hardened runtime and a secure timestamp: `kiko`, each helper in `native/` and `bin/tmux`, each as `sh.kiko.<file>` (the prefix is `src/core/name.ts` `IDENTIFIER`, read by `release.sh`; the keychain helper's `sh.kiko.keychain` is what the Keychain trusts with the keys), and the helper app inside out: each helper in its `Contents/Helpers/` as `sh.kiko.helper.<helper>`, then the bundle as `sh.kiko.helper` (`name.ts` `flavourNames("release").helperAppId`; `release.sh` stops if it isn't `IDENTIFIER.helper`, what updates check it as). **The helper app isn't stapled:** stapling writes a file into the bundle after it's signed, and the fast path publishes before notarizing, so a stapled bundle would differ between the two paths; unstapled, the files published are the same either way, and Gatekeeper looks its ticket up online by its hash, as for every bare executable (`curl` and `kiko update` don't quarantine it anyway). The bundle and each of its helpers is in the ticket (notarized.ts counts the helpers on their own), and `gatekeeper.ts` assesses a quarantined copy of the whole bundle as an app (`spctl --assess --type execute`). Both chips then go to Apple's notary service in one zip (`xcrun notarytool submit --wait`, the profile `KIKO_NOTARY_PROFILE` names, `kiko-notary` by default), and the build stops unless it says Accepted (Apple's log is saved as `dist/notary-log.json` when it doesn't). A bare executable can't have its ticket stapled, so Gatekeeper finds it online by the code's hash when a downloaded copy first runs. Before packing, the script checks that Apple's log of the submission lists every file's hash and that Apple's ticket service serves a ticket for each, the lookup Gatekeeper makes (`scripts/signing/notarized.ts`), and then that this Mac's Gatekeeper accepts a quarantined copy of each, as it would a browser download (`scripts/signing/gatekeeper.ts`): `spctl --assess --type open --context context:primary-signature` on a copy carrying Safari's `com.apple.quarantine`, which looks the ticket up online and must say `accepted`, `source=Notarized Developer ID`. That's the assessment that reflects a quarantined launch of a bare executable; `spctl --type execute` says "does not seem to be an app" of any bare one, notarized or not, and `syspolicy_check distribution` "Notary Ticket Missing" (it wants a stapled ticket). Gatekeeper is asked again every 10 s, for up to 10 minutes (`KIKO_GATEKEEPER_TIMEOUT`, seconds), because for a few minutes after Accepted Apple's ticket service can still answer "not found" to this Mac's Gatekeeper after notarized.ts was served the ticket: 0.2.0 (2026-11-01) was packed 33 s after its submission, a quarantined copy launched 2 minutes later got "Apple could not verify 'kiko' is free of malware" (Gatekeeper was told "not found" until about 4 minutes after), and the same copy is accepted since (as is HashiCorp's notarized `terraform`, the same kind of bare executable, and refused is a Developer ID one never notarized). **No release check ever starts a quarantined copy**: one that isn't accepted puts Gatekeeper's dialog in front of whoever is at the Mac and leaves the launch waiting on it; assess with `spctl` instead. Files fetched with `curl` aren't quarantined, so Gatekeeper doesn't check them on install anyway; a browser download would be, and passes.
- **Third-party notices** (`THIRD_PARTY_NOTICES.md` in each tarball, `scripts/notices/notices.ts`): made from what the release holds, so it can't drift. `scripts/bundle.ts` writes Bun's metafile (`meta.json`, every file that went into the bundle) beside the bundle; every npm package one of those files came from is listed with its version, licence id and full licence text (and NOTICE file), read from its folder in `node_modules`. Packages the bundle doesn't draw from aren't (e.g. `ws`: the bundle's `import "ws"` is Bun's own built-in one). Then Bun's licence (`scripts/notices/bun/LICENSE.md`, Bun's own, kept for the Bun in `bun/VERSION`) and tmux's (`build-tmux.sh`'s notices). Code ported from another project into a file of Kiko's own (not a package, so not in `node_modules`) is listed in `PORTED` in `notices.ts`, with the files that carry it and its licence text in `scripts/notices/ported/` (from the project's repository at a pinned commit); it goes in whenever one of those files is in the bundle, and each of those files keeps the project's copyright and licence in its header (`release-notices.test.ts` checks both). Today: voice-glow 0.5.0 (MIT, Libraries.dev), ported in `src/ui/dither-glow.ts` and `src/ui/voice-envelope.ts`. Right after bundling, `release.sh` runs it as a check and **stops** if a bundled package has no licence text or the Bun building isn't the one `bun/LICENSE.md` is from (it prints the `curl` that refreshes it; read what changed). A package that publishes no licence file gets one in `scripts/notices/supplied/<name>.txt`, from its repository at a pinned commit or tag, listed in `SUPPLIED` with where it's from (today `yoga-layout` and `standardwebhooks`); it's used only while the package declares the same licence. A GPL-family licence (GPL, LGPL, AGPL) or one the check doesn't know is printed as "needs care", without stopping the build: Bun's statically linked JavaScriptCore (LGPL-2.1) always is. `tests/unit/core/release-notices.test.ts` also checks that every production dependency has a licence text, so a new dependency without one fails `pnpm check` rather than the release.
- **Before building, a release checks** that the identity is in the keychain and its key signs (which also reaches Apple's timestamp server), that the notary profile works (`notarytool history`), and that the tools are there, and stops at once with what's wrong. After signing, each file must verify (`codesign --verify --strict`) with the hardened runtime, the identity, a timestamp and its entitlements, and meet the very requirement installed copies check updates with (`src/core/updates/verify.ts` `requirement`: a Developer ID Application certificate of `name.ts` `TEAM`, `YU89X2P36Z`, and `sh.kiko.<file>`), so a build signed by another team stops here instead of being refused by every Mac.
- **What updates and install.sh check** (ARCHITECTURE.md, "Updates"): every executable against that requirement, the helper app with `codesign --verify --deep --strict` against the same requirement for `helper` (everything in the bundle sealed by its signature), then the new `kiko _verify-files`: `kiko` is built last, with the SHA-256 of every other file in its folder (scripts, terminfo, notices, the signed helpers) baked in (`scripts/signing/release-files.ts`, `--define __KIKO_RELEASE__`), so its signature covers them; it checks its folder holds exactly those and prints its version, which must be the feed's. The helper app's files aren't in that list: the bundle's own signature vouches for them, and the list carries its folder's name and its requirement instead, which `_verify-files` checks it against (`release-files.ts` `checkBundle`), so an update checked by an older `kiko` (whose `verifySignatures` doesn't know the bundle) still has it checked by the new one. `release.sh` runs that check on this chip's folder before packing. So **nothing may be added to or changed in a chip's folder after `kiko` is built**, and the feed's `version` must be the one built (`KIKO_VERSION`), or every installed copy refuses the release. An ad hoc build (`KIKO_SIGN_IDENTITY=-`) has "takes ad hoc updates" baked in; install.sh takes one only with `KIKO_INSTALL_ADHOC=1`.
- **Entitlements** (`scripts/signing/`): `kiko` gets `com.apple.security.cs.allow-jit` (without it the hardened runtime turns Bun's JIT off: everything runs, about twice as slow) and `allow-unsigned-executable-memory` (Bun's guide has both; kept for Intel Macs, which couldn't be tried on real hardware). No `disable-library-validation` (no native addons) and no `disable-executable-page-protection`. `mic`, `permissions` and the helper app's bundle get `com.apple.security.device.audio-input`: under the hardened runtime a program without it gets nothing from the mic. The helper app's bundle also gets `com.apple.security.automation.apple-events` (`scripts/signing/helper-app.entitlements`): it runs the AppleScripts that control Ghostty, iTerm and Terminal, and under the hardened runtime they're refused without it. The rest get none (speech recognition has no entitlement, and `speech` only reads the audio `mic` sends it; tried signed: it transcribes). The helper app's `Info.plist` has the microphone, speech recognition and Apple Events (`NSAppleEventsUsageDescription`) reasons macOS shows when it asks for "Kiko"; `mic`, `permissions` and `speech` carry the same in an Info.plist linked into the binary.
- **Settings:** `KIKO_SIGN_IDENTITY` (the identity's name or SHA-1) and `KIKO_NOTARY_PROFILE` (`off`: signed, not notarized, said as not for uploading). The profile is made once with `xcrun notarytool store-credentials kiko-notary --apple-id <your Apple ID> --team-id <team id>` (it asks for an app-specific password, made at account.apple.com, and keeps it in the keychain; nothing in the repo); a profile you already have works as well: set `KIKO_NOTARY_PROFILE=<its name>` in your shell, which `pnpm ship`'s background notarizing inherits too. Without one, `release.sh` stops before building with a line saying the profile isn't in the keychain.
- **Ad hoc, for this Mac and the tests:** `KIKO_SIGN_IDENTITY=- pnpm release:build` signs ad hoc, still with the hardened runtime and the same entitlements (so it runs as a release does), and sends nothing to Apple: seconds instead of minutes, and no Apple account. The tests build that way (`install-live`, `early-access-live`). `KIKO_TEST_DIST=<folder> pnpm test:live` runs `install-live` on a release built before instead, e.g. a signed and notarized one built with `KIKO_DIST=<folder> KIKO_RELEASES_URL=file://<folder>`.
- **The Keychain asks once more, once:** keys saved by an ad-hoc-signed keychain helper (an early build, or a checkout's on a Mac without a developer identity) trust that binary's hash alone, so the first read by the Developer ID one gets macOS's "wants to use your confidential information" prompt; Always Allow, and from then on it's the identifier and the team that are trusted, so later updates ask nothing.

1. Set `version` in package.json, commit.
2. `KIKO_RELEASE_NOTES="what's new, in a line" pnpm release:build`. It checks the signing first (above), then writes `dist/` (git-ignored): both chips, built at once (x64 is left out, with a warning, if Bun can't fetch its x64 runtime or tmux doesn't build), signed and notarized (`KIKO_NOTARIZE=later`: signed only, for notarizing after publishing), the checksums and `latest.json` with URLs under `KIKO_RELEASES_URL` (default `https://kiko.sh/releases`). About 41 MB (arm64) and 44 MB (x64) packed; tmux is 0.8 MB of that (2.1 MB unpacked). About 15 s plus Apple's notarizing and the Gatekeeper gate (4 to 5 minutes).
3. Try it as a user would, in a throwaway home, from a build whose URLs point at dist/ itself (then build again without it for uploading):
   ```sh
   KIKO_RELEASES_URL=file://$PWD/dist pnpm release:build
   HOME=$(mktemp -d) KIKO_RELEASES_URL=file://$PWD/dist sh install.sh   # an ad hoc build: KIKO_INSTALL_ADHOC=1 too
   ```
   `tests/live/cli/install-live.test.ts` does this (no agent installed, the Claude Code offer, the PATH line, the bundled tmux running Kiko's server, a second version, a bad checksum, refusals: a relabelled build, a changed hook, a helper signed by someone else, an ad hoc build without `KIKO_INSTALL_ADHOC`; `kiko uninstall`, each file's signature) in `pnpm test:live`, with a PATH that has no tmux, on an ad hoc build of its own; `KIKO_TEST_DIST=$PWD/dist pnpm test:live` runs it on the one just built (its URLs pointing at dist/, as above).
4. Upload: the tarballs and `.sha256` files first, `latest.json` last, so the feed never names a file that isn't there, from the site's checkout: `pnpm exec wrangler r2 object put kiko-releases/<file> --file <dist>/<file> --content-type … --cache-control … --remote` for each (the site's RELEASES.md has the types and caching).
5. If `install.sh` changed: `scripts/sync-site.sh` (it finds the website's checkout; `KIKO_SITE=<folder>` to choose), commit and push it there, then `pnpm exec wrangler deploy` in it.
